# Automation access and local approval

The existing control-API token continues to authenticate with full capabilities. It is not rotated or silently restricted. Named client tokens are optional additions, managed in the local **Automation access** window. Only token hashes are saved; copy a newly generated token to the intended client's `GLDRIVE_CONTROL_TOKEN` environment variable. Existing registrations can continue reading the legacy token as before.

Named clients start with `Observe` only. Additional scopes are `Operate`, `Configure`, `Secrets`, `RemoteAdmin` and `LocalFiles`. Exact tool-family restrictions, expiry, and explicit permission for destructive actions can further narrow a client. An empty family list permits all families within its scopes. An empty local-root list permits no explicit local-file paths; selected roots allow canonical descendants without junctions or symbolic links. Legacy access is unaffected by these optional restrictions.

Security settings live under `controlApi.security` and are edited locally. Automation cannot change this policy or grant itself scopes. Scoped clients cannot rotate the owner token or change the listener through patches or timed settings. The legacy owner can still explicitly edit its token and listener. Historical and portable restores retain the current listener and security policy. Settings-dialog saves preserve the latest saved policy. A malformed optional security block is retained for repair and disables scoped clients without discarding ordinary configuration or disabling the legacy token.

## Approval behavior

`requireDangerousApproval` defaults to `true` for scoped tokens. The existing owner token retains its previous immediate behavior for every tool, including sensitive operations. `requireLegacyApproval` defaults to `false`; a local user can explicitly enable it to apply the selected approval rules to the owner token. Enabling it can interrupt unattended clients. Approval covers secret reveal or replacement, remote administration, and destructive local deletions or overwrites. Parameter-sensitive reads such as credential presence, redacted config, and ordinary UI navigation, selection, search, playback, dismissal and clearing finished race cards do not prompt.

`requireConfigurationApproval` independently defaults to `true` for scoped clients: explicit edits to saved application settings require local review. Ordinary owner `config_patch` calls never prompt with the default settings. This covers a writing `config_patch`, starting a setting lease, restoring settings, reverting an experiment, and selecting a Plex server. Ordinary configuration is not classified as secret. Previews, lists, a patch containing only tests, snapshot/experiment bookkeeping and non-secret installer form edits do not prompt. The tuning agent retains its validator and consent rules; Plex sign-in retains its browser authorization. All three approval switches are editable in the local access window.

A configuration patch awaiting approval is bound to its settings revision. A concurrent edit or server reorder makes the approved patch fail its revision precondition; read the latest settings and request a fresh edit. An explicitly supplied `expectedRevision` is retained.

Raw FTP commands are administrative by default. Only the exact no-argument commands `PWD`, `SYST`, `FEAT`, `NOOP`, `SITE WHO` and `SITE HELP` are read-only. Additional arguments or control characters cannot turn an administrative command into a read. The existing pooled connection and login-budget behavior is retained, including discarding a connection used by `ftp.command`; no new polling or eager connection pool is introduced.

The nonmodal local approval window identifies the caller and operation, with selected targets or paths where applicable. It includes stable item IDs, resolved wishlist/download titles, release names, sections and status filters. Raw IRC prompts show the verb and target with the body omitted. It never displays submitted passwords, tokens, key values or raw command bodies. `approvalTimeoutSeconds` defaults to 120 seconds, with a range of 5–600. Timeout, denial, a locked desktop or shutdown denies the operation. Only the automation job waits; engine threads, racing, logins and ordinary UI actions continue.

Pending approvals have a separate 64-request budget and never occupy the 16 execution slots. Old pending decisions expire to deny. Slow approval returns a job with status `awaiting-approval`. After approval, the ordinary execution-capacity check still applies. Fast denial and a locked desktop return a job with status `denied` and code `approval_denied`, just like a later denial. Scope refusals use HTTP 403 with code `scope_denied`; authentication rejection remains HTTP 401. The MCP bridge returns these refusals as tool errors and keeps the same connection and credential, without retry or rediscovery. Poll `app.jobs_get` for the final `completed`, `denied`, `failed` or `cancelled` status. Jobs and results belong to the requesting client. Scope reduction prevents retrieval of an earlier secret-bearing result; revocation, expiry or token rotation while approval is pending prevents execution. Owners can still list and cancel their own jobs without a tool-family restriction hiding the polling tools.

When owner approval is explicitly enabled, destructive UI invocations bind the selected stable identities before approval and verify the same selection immediately before invoking the existing command. Changing the selection invalidates the approval. Installer start and extractor start/settings similarly bind the connected destination, profile or archive queue used by the pending operation; changing those targets requires a fresh approval. Scoped clients use stable-ID domain tools for deletions instead of mutable UI selections. Scoped extractor start/settings operations are unavailable because their saved queues can contain paths outside a request; use the local extractor for those actions.

## Call evidence

`ledgerEnabled` defaults to `true`. The append-only [automation ledger](automation-ledger.md) records bounded, redacted argument shapes and outcome events, including rejected calls, without storing results or exception text. `ledgerCapacity` defaults to 2,000 recent in-memory entries, with oldest eviction; disk segments have separate fixed byte bounds. These are passive evidence bounds, not call or engine rate limits. An unavailable ledger keeps bounded memory and warns once; it never refuses an otherwise authorized operation.

Configuration writes retain the stable `mcp:<tool>` human actor for owner and scoped clients. Client identity and call correlation remain in the ledger, never in the AI undo audit reference.

This implementation adds no per-client FTP login cap. Existing account-wide login admission remains authoritative. Event subscriptions, general telemetry aggregation and MCP playbook prompts are separate follow-up work.
