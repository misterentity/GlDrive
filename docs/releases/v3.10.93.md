# GlDrive v3.10.93 release record

## Findings and root causes

- Production logs contained no current `ERR` or `FTL` application records. SYN's FTP endpoint
  remained unreachable by direct TCP probe, while intermittent FXP `425` data-channel failures
  completed on the existing retry path.
- Fresh-runner CI exposed an unsynchronized updater-key check/create/write race. Parallel callers
  could persist different DPAPI keys, invalidating a newly written authorization immediately.
- Live deployment found that the fixed-action SYSTEM task routed through WPF startup and could
  exit before consuming its handoff.
- After moving dispatch to `Program.Main`, live ProgramData diagnostics exposed two more task
  boundary defects: SYSTEM cannot resolve/decrypt the interactive user's CurrentUser-DPAPI
  authorization marker, and handoff cleanup was in a `finally` after `ApplyUpdate`, which
  intentionally terminates its own process and therefore never returns.

## Changes

- Synchronize updater-key initialization and publish new keys by atomic same-directory rename.
- Dispatch both updater modes before WPF construction.
- Preserve HMAC authorization for interactive elevation. In fixed-action SYSTEM task mode, pin
  the destination to the task executable and verify the strictly newer version, RSA publisher
  signature, and locked archive hash before and after application shutdown.
- Consume the task handoff before the non-returning applicator and refuse dispatch if deletion
  fails.
- Record SYSTEM entry, handoff acceptance/rejection, and dispatch in
  `%ProgramData%\GlDrive\update-task.log`.
- Add cold-start concurrency, privilege-boundary, entry-order, and handoff-consumption regression
  coverage.

## Remaining risks

- SYN remains externally unreachable; GlDrive's bounded remount loop continues to handle it.
- Remote FXP endpoints can still refuse transient data connections; observed failures recovered
  on retry, so no application change was warranted.
