# GL Drive v3.14.0

Feature-gap roadmap, Phase B batch 2. Codex implemented it and Claude reviewed it. The review changed eight behaviours before release; they are listed under *Review fixes*. Full suite: 3,731 tests (3,658 app, 53 core, 20 MCP), 0 failures.

## Site health and login protection (on by default)

- **Persistent retry ladder.** A site whose FTP logins fail keeps the existing 30-second to five-minute ladder for the first 30 minutes, then retries after 15 minutes, 1 hour and 4 hours. The schedule survives restarts. A site that has been down for days now gets a handful of attempts a day instead of one every five minutes.
- **One notice per outage.** The tray shows one "FTP outage" notice and one "FTP recovered" notice, not a balloon on every retry. Manual retry still works at any time.
- **Account login budget.** `servers[].pool.loginRateLimitEnabled` (default on) and `maxLoginAttemptsPerFiveMinutes` (default 8) cap new logins per account. Successful logins count too, and one slot stays reserved for `!user` ghost recovery. Reusing a pooled connection costs nothing. In the last 2¼ days of real logs, the busiest account peaked at 4 logins in any five minutes, so normal use has twice the headroom it needs.
- **Optional TCP probe.** `health.tcpProbesEnabled` (default off) checks a long-unreachable site with a five-second TCP connect before a full login, at most once every 15 minutes. It honours SOCKS5 and never scans the LAN.
- **Announce-feed health.** `health.announceSilenceAlertsEnabled` (default on) learns each channel's hour-of-week announce rate. It alerts once when a channel is silent for at least an hour and the silence has under a 0.1% chance by that rate. Baselines need about two weeks of data before any alert can fire. `health.announceRecoveryEnabled` (default off) lets a missing configured channel rejoin through the existing invite path.
- The Mounts cards show health and the next retry, and hovering over the pool slots shows what each borrowed connection is doing. `servers.get` and `irc.status` expose the same detail over MCP.

## Race controls and own-account nukes

- Race cards now have working Stop and selection, plus a safe **Reset** that clears failure counters at the next scan boundary.
- You can add a site to, or remove one from, a queued race. A confirmed cleanup of an owned partial goes through the existing ownership and incompleteness checks.
- **Re-race** from history reports the real admission result.
- **Own-account nuke alerts** (`spread.ownNukeAlertsEnabled`, default on). A trusted sitebot NUKE line or the existing `SITE NUKES` poll that names your account as nukee raises one alert. Alerts are de-duplicated across restarts and add no FTP traffic.
- Releases with exact nuke evidence are never raced again or cleaned up.

## Wanted list and series (opt-in)

- `downloads.wantedDecisionWindowEnabled` collects variants of a wanted release across sites for 15 minutes, then grabs the best one that has a trusted completion hint. `downloads.wantedIndexSweepsEnabled` checks existing search indexes when the wanted list changes, with no extra FTP traffic. Both are off by default.
- **Series monitoring** is set per TV item with `monitorMode` (`Future`, `Missing`, `All` or `LatestSeason`). Existing items stay `Legacy`, which keeps today's behaviour.
  - A daily episode inventory feeds the MCP tools `wishlist.series`, `wishlist.season_plan` and `wishlist.season_pull`.
  - Pulls of finished races from an explicitly listed server (`downloads.raceCompletedPullsEnabled`, `racePullServerIds`) stay off until enabled.
  - Background pulls give their connection back to racing.

## Review fixes

The review checked every new default-on limit against real logs, then:

- **Fixed a pre-existing login storm** (from 3.11.0). For any download, the "idle race login" second stream asked for the source site's race login every 5 s with a 2 s wait. When the race pool was empty, each ask started a fresh login. That login takes about 2 s, so it was cancelled just as it finished and thrown away: 253 logins to the source site in one hour, and 58 in five minutes, on 10-27. Under the new budget, that churn would have used up the account's logins and starved race logins.
  - A login that is still connecting when the wait ends now finishes into the pool, and the next ask uses it.
  - Failed asks back off 5 s, 10 s, 20 s and so on, up to 5 minutes.
- **No local state file can hold logins, races, IRC joins or telemetry any more.** As written, an unreadable or unwritable `site-health.json`, `ftp-login-governor.json` or `nuke-observations.json` would have held every automatic login or every race. The nuke store would also have reached that state on its own once it held 10,000 nukes. Now:
  - An unreadable file is copied to `<name>.corrupt` and tracking restarts empty.
  - A failed write keeps state in memory.
  - Full stores drop their oldest entries.
  - The same applies to the age-only nuke telemetry cursor.
- **A bare `421`/`450` no longer means a two-hour BNC cooldown.** Most daemons send these codes for "too many users". Only a server reply with explicit throttle text earns the two-hour hold. GlDrive's own "Server in BNC cooldown" message is never treated as server evidence.
- **Login-limit replies and dropped live connections are not outages.** The site answered, so these no longer arm the retry ladder. Before this fix, the ladder could also block the `!user` ghost kill that clears stale sessions.
- **IRC invites follow the FTP connection, not the recorded health state.** The draft gated SITE INVITE on health state and parked a refused join for 30 minutes. One transient login failure could therefore keep an invite-only announce channel unjoined for hours. A parked join now re-checks every minute and re-sends the SITE INVITE it skipped.
- **Truncated nuke names never hold a race.** `SITE NUKES` cuts `Dir:` at about 50 characters, often inside the group name, so a prefix match can point at your release when another group's copy was nuked. A truncated name now names the alert only.
