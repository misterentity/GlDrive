## Log review

The complete v3.10.98 production session (2026-09-01 21:37:04 through the v3.10.99
handoff on 2026-09-02 09:38:14 local time) contained **31,296 structured records: 0 ERR,
0 FTL, and 37 WRN**. Windows Application Error, .NET Runtime, and Windows Error Reporting
also contained no GlDrive failures during the review window.

The warnings were accounted for as follows:

- 15 were the known SYN FTP host outage: the initial failed mount plus bounded remount
  reporting. SYN IRC remained connected independently.
- 18 were paired path/detail records for nine individual FXP failures. Seven were transient
  `425` data-connection refusals; the affected connections were quarantined/recreated and
  the races completed. Two `550` failures occurred after a source migrated a release away
  during the race; the app detected and reported that external condition.
- Three were one-off NewReleaseMonitor poll failures. The next poll succeeded in each case;
  none became a consecutive outage.
- One reported the source migration associated with the `550` pair above.

The error-level sweep was clean, but two persistent data-quality defects were visible through
the authenticated Control API and detailed race traces. In the retained v3.10.98 session
sample, **43 of 57 races** reported `filesDelivered > filesTotal`, and **13 of 57** expected
duplicate/no-work jobs were stored as `Failed/config`.

## Root causes and changes

| Area | Root cause | Resolution |
|---|---|---|
| Spread file totals | Once an SFV was parsed, progress and history used the SFV entry count plus the SFV itself as the entire release total. Ancillary files discovered on the source (NFO, sample, subtitle, proof, and similar files) were still counted as owned/delivered, making the numerator exceed the denominator. | Added `SpreadJob.ResolveFileTotal`, which uses the larger of the SFV lower bound and the discovered-file count. Cleanup, scan reconciliation, and progress projection now share that rule. |
| Duplicate/no-work terminal state | `SetFailed` set `State=Failed` and `LastError` before recognizing the existing-on-both-sites outcome as expected. Only the log severity was downgraded, so history still persisted a configuration failure and emitted the error event. | Expected no-work outcomes now terminate as `Completed`, clear `LastError`, log at information, and do not emit the error event. Actionable failures retain the original failed/error behavior. |

The project version and changelog were advanced to 3.10.99. Regression coverage was added in
`SpreadFileTotalTests` and extended in `SpreadNoWorkLogPolicyTests`.

## Remaining risks

1. No new transfer-bearing race began during the immediate post-deploy observation window.
   The corrected file-total invariant is covered by focused tests and is present in the
   attested production binary, but the first natural race with ancillary files should still
   be checked for `filesDelivered <= filesTotal`.
2. SYN's FTP endpoint remains externally unavailable. The bounded remount loop is healthy,
   SYN IRC remains connected, and this release does not change that long-running outage.
3. Isolated `425` data-connection refusals and a source moving files away mid-race remain
   possible external FTP conditions. Existing quarantine, retry, and source-migration logic
   handled them during the reviewed session.
4. The installer is not Windows Authenticode-signed. The auto-update path did verify the
   RSA-signed checksum manifest and the ZIP's SHA-256 before installation, but a user who
   downloads the standalone installer does not receive an Authenticode publisher identity.
5. Production still uses `loginHeadroom: 2`, which limits effective FXP concurrency to one
   reserved transfer login per site. This is an operational configuration choice, not a
   release regression.
