# v3.10.138 — attribute FXP transfer deadlines and release their tracking

## Findings and changes

The September 29 review started from installed version 3.10.137 (PID 65740,
started September 28 10:18:58 PT). The three retained daily logs (September
26–28, through 20:00:48 PT) contain **0 Error and 0 Fatal** records and
**73 / 86 / 75 Warning** records per day. The warning volume is flat and all
warnings are classified:

| Warnings (3 days) | Classification |
| --- | --- |
| 144 | Downloads parked because `T:\` is not mounted (external, unchanged) |
| 67 + 2 | SYN remount / mount timeouts: host still unreachable (external) |
| 3 | SYN IRC connection failures (same host outage) |
| 10 | Five FXP failures: source relocated `/incoming` → `/recent` mid-race, followed by the relocation handler; all races completed |
| 3 | Relocation notices (expected, handled) |
| 2 | Extraction parked for disk space on `D:` (external, unchanged) |
| 1 | OpenRouter HTTP 429, recovered by the 2-minute catch-up |
| 1 | Release-listing timeout, recovered next poll |
| 1 | NukePoller borrow cancel at 08:20 on 3.10.137's predecessor; fixed by 3.10.137, none since |

Races on the working route (superbnc → zephyr) completed normally after the
3.10.137 deploy. Duplicate IRC announces were suppressed as designed.

The review also covered Information-level output. At **17:33:57 PT** both
sides of a superbnc → zephyr Relay transfer were quarantined with
`poisoned-discard: FXP job cancelled mid-transfer`, yet that race kept running
and completed at 17:38:05. The job was not cancelled. The transfer had hit its
own **180 s per-transfer ceiling**: 3 × `transferTimeoutSeconds` (60).

Root causes:

- **Misattribution.** The per-transfer token is linked to the job token.
  `catch (OperationCanceledException) when (ct.IsCancellationRequested)`
  therefore could not distinguish a stopped race from a transfer that hit its
  own deadline. Every ceiling hit was logged only as a job cancel, with no
  warning and no failure counted against the file/route retry limit. A file
  that always hits the ceiling could be re-picked indefinitely, costing two
  logins per attempt.
- **Leaked tracking.** `_activeTransfers.Remove` ran only on the normal return
  path. Any thrown transfer left a phantom entry, which had three effects:
  - the race's end-of-job drain waited its full 60 s before cleanup
  - stale-slot detection (`claimed > 0 && tracked == 0`) was masked
  - the dashboard showed a transfer that no longer existed for the rest of the
    race; the update gate also counted it, because it keys on
    `ActiveTransferList`
- **Invisible in telemetry.** `FxpTransfer.ExecuteAsync` emitted no telemetry
  row when a transfer was cancelled. Ceiling hits therefore did not appear in
  the digests the AI agent reads either.
- **Unreachable inner timeout, and one mislabel.** Relay's own 1200 s deadline
  (20 × 60) can never fire before the 180 s outer ceiling. If it ever did (with
  `transferTimeoutSeconds` = 0), its exception reached the catch labelled
  "borrow timeout" and returned mid-command sessions to the pool unpoisoned.

Changes:

- `FxpFailurePolicy.ClassifyCancellation` attributes each cancellation from the
  job token, the transfer token and whether protocol had started:
  `JobCancelled`, `TransferDeadline`, `SetupDeadline` or `BorrowTimeout`.
  `ExecuteTransfer` now receives the job token.
- **TransferDeadline** poisons both sessions, bumps the (file, src, dst) failure
  count and logs `FXP transfer timed out: … after Ns, bytes moved X of Y (mode,
  ceiling, attempt N)`. Bytes are only measured in Relay mode; server-to-server
  modes report `unmeasured` rather than a false zero.
- **SetupDeadline** (the ceiling fires while still waiting on gates or borrow)
  is logged at Information. The peers are pristine and are not poisoned.
- A job cancel before protocol start no longer poisons pristine peers. This is
  consistent with `ShouldPoisonPeers`.
- Active-transfer tracking is a scope (`TrackActiveTransfer`). It is released
  in `finally`, is idempotent, and never removes a newer registration of the
  same key.
- Cancelled transfers now write a telemetry row with `abortReason: "cancelled"`,
  then rethrow unchanged. `TransfersDigester` computes its Kbps matrix from
  completed transfers only. Measured over September, aborted rows shifted it
  by only 0.4 %, but they are not throughput measurements.
- `FxpFailurePolicy.TransferCeiling` is now the single definition of the
  per-transfer ceiling. **The 180 s value is unchanged**, for the reason below.

Ceiling sizing was examined and deliberately not changed. Across **50,669**
successful September transfers, p50 is 10.5 s, p99 46.5 s and the maximum
165.5 s. Only 3 exceeded 120 s. There is one ceiling hit in three days, and the
log cannot tell whether that transfer was slow or wedged, so raising the
ceiling would be a guess. The new warning records elapsed time and relayed
bytes, so the next sweep can tell.

Version is 3.10.138. No configuration or persisted-data migration is required.

## Remaining external conditions and limits

- **SYN** FTP endpoint is still unreachable: remount attempt 111 at 20:00 PT
  timed out, and the retry loop is working as designed. The host must be
  restored upstream.
- **T:** is not mounted. Two downloads (Backrooms.2026, Stop.That.Train.2026)
  re-park every hour without consuming retries. Windows authentication to
  `\\zephyr\tv` must be restored.
- **D:** lacks space for the parked `Dont.Be.Shy` archive set, and extraction
  stays parked. User media was not touched.
- The ceiling fix is verified by unit tests and code paths. No real 180 s
  ceiling hit is reproducible against the loopback fixture, so the first
  production `FXP transfer timed out` line is the live confirmation.
- A transfer that is slow but alive for more than 180 s is still cut off, as
  before. It now counts toward the per-pair retry limit, so a file that
  repeatedly needs longer than the ceiling will exhaust its retries on that
  route instead of looping. If warnings show relayed bytes still climbing at
  the ceiling, the next step is a progress-aware (stall) deadline.
- Native smoke does not exercise a remote glftpd BNC's CPSV behaviour. A short
  post-deploy window cannot establish multi-day stability.
