## Changes and underlying causes

- Player **Download** now adds torrent content to the persistent main Downloads queue. The application owns a dedicated lazy MonoTorrent engine, independent of the player window and streaming session. The previous transient player-owned list could not provide that shared lifetime and durable queue behavior.
- The common manager supplies scheduling, pause/resume, cancel/retry, persisted progress, disk reservations and optional extraction. MonoTorrent supplies metadata, peer transfers and piece verification through a whole-item source; FTP retains its existing transfer engine and the v3.11.13 connection-sharing fixes.
- Metadata and destination/file policy are checked before payload registration or writes, including cached metadata on resume. Escaping paths remain non-overridable. Mixed blocked content requires explicit consent to skip blocked files; a torrent with no permitted files is rejected. Each queued torrent owns a dedicated destination subfolder.
- Completion requires verified selected pieces and stopped writers before extraction or a Completed state. Immediate resume/retry waits for the previous operation to relinquish ownership. Paused items remain protected from watch-folder extraction, and removing history cannot release a still-active writer's ownership.
- Pinned MonoTorrent behavior exposed two lifecycle causes: default removal deletes cache data, including fast resume; and asynchronous startup/hash continuation can replace a prematurely stopped state. The adapter uses `KeepAllData`, preserves checkpoints around metadata probes, and waits for startup/hash settlement before stop/removal. Owner/session cleanup also moves outside their opposing locks to remove a shutdown lock inversion.
- Persisted byte counts cannot establish on-disk integrity. Disk admission therefore reserves the full selected torrent size before verification instead of subtracting possibly stale progress.
- Automation enumerates the shared queue catalog and routes controls by the actual queue owner, including legacy rows without stored owner IDs. Detached public projections retain normal download fields and source/status details while omitting tracker-bearing magnets. Magnets remain persisted locally for resume; they are not encrypted by this change.

### Initial CI failure and deterministic correction

CI **38801999270** for earlier commit `a792818bb0e045d9e72b4315b5d5b48d753d2d50` failed the real-peer test's cancellation assertion. Its 512 KiB loopback payload could finish before a 10 ms progress poll saw a partial value. That run was **not a successful release gate** (`release/ci-failure.log`).

The fixture now gives its only reachable peer exactly **one hash-valid 16 KiB piece**. The remaining pieces are unavailable, so full completion is impossible until the cancellation observer runs. Assertions require exactly 16,384 verified bytes at interruption and one available peer piece. Only after downloader cancellation, checkpoint saving and writer closure does the fixture stop the source, replace its bytes, explicitly hash-check them, and restart it with full availability. Rate caps were removed; no larger payload, arbitrary delay or relaxed cancellation assertion is used.

Both phases still require actual received peer bytes. The second phase creates a fresh downloader engine, checks checkpoint bytes survived preparation, downloads the remaining data, obtains exclusive access after writers close, and verifies the final SHA-256. DHT, discovery, port forwarding and trackers are disabled; the sole listener and injected peer are loopback. This establishes local engine transport and restart behavior, not public-swarm availability.

## Remaining risks and limits

- One configured FTP site remains unreachable with backed-off remount attempts; the same site was offline before deployment. IRC invitation requests and three invite-only channels remain unavailable on another site. These require external service/access resolution.
- The repeated extractor warning concerns the same preexisting incomplete archive. Read-only inventory found only 3 of 15 SFV volumes and 12 matching zero-byte missing markers; readiness correctly blocks extraction. The missing source data was not altered or recovered. See the [FTP deployment report](v3.11.13-deployment.md).
- Production observation was a five-minute health/transfer window, followed by a bounded log audit; it is not a long-running soak. The updater’s shared forced-exit status requires independent file and health verification.

- The installer emitted the existing Inno per-user-area advisory: `installer/GlDrive.iss:22` requests administrative install mode, while line 56 writes the selected autostart task to `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run`. That source is unchanged from v3.11.13. In an alternate-admin credential installation, autostart can therefore be assigned to the administrator running Setup rather than the initiating user's account; this is an inference from the script and Inno's documented account behavior. Fresh installation under that alternate-admin context was not runtime-tested. Installer compilation succeeded; this is a retained installer behavior/coverage limit, not a compile failure or evidence that the signed-ZIP update path failed. Production deployment used the existing SYSTEM signed-ZIP updater, which does not execute this installer registry entry. Sources: [Inno privilege/account behavior](https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm), [administrative install mode advisory](https://jrsoftware.org/ishelp/topic_admininstallmode.htm). Evidence: `release/release-pipeline.log`.
- FTP's shared byte pacer and MonoTorrent's engine cap remain separate bandwidth budgets. Matching settings do not create one aggregate application bandwidth ceiling.
- Full selected-size reservation on torrent resume is conservative and can reject admission on a nearly full volume even when existing valid pieces would reduce remaining network bytes.
- Local isolated tests do not establish public/private swarm reachability, metadata availability, throughput or tracker service health. No production torrent workload was initiated for this verification.
- Current VPN handling binds incoming listener/DHT endpoints; outgoing torrent peers can still follow the default route. This release does not claim comprehensive VPN isolation or a kill switch.
- Pause/shutdown during startup or hashing waits for that owned work to settle. A bounded application shutdown can still expire before drain finishes, requiring piece rechecking after restart; no retry may take over the same writers prematurely.
- Blocked files can share pieces with permitted files. Existing skipped-file cleanup and crash limitations remain; this integration does not promise forbidden bytes can never temporarily exist after an abnormal process exit.
- Persisted magnets and torrent metadata may include tracker credentials. Public automation projections omit magnets; local persisted/cache data relies on its existing Windows access controls, not encryption introduced by this release.
