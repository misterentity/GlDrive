## Defect 1 — a Windows restart was reported as a crash and GlDrive was relaunched into it

Evidence: System event 1074 at **17:07:46** shows the user restarting the PC from the Start
menu. GlDrive logged `GlDrive shutting down...` at 17:07:51. At 17:07:54 the watchdog logged
`exited without a clean-exit marker … Restarting` and launched PID 12156 into the
shutting-down OS. The machine rebooted at 17:09. On the next start (17:13:02) GlDrive logged
`restarted by watchdog after unclean exit` and showed the user a *"Previous shutdown did not
complete"* tray balloon.

Root cause: `App.OnExit` deleted the `.running` crash marker only as the **last** step of a
teardown that takes several seconds (it disposes the AI runner, the control API, every server
mount and the spread pools). Anything that ends the process during teardown leaves the marker
saying "running". That includes a Windows restart or logoff, and also the tray **Exit**
command's own 3-second `Environment.Exit(0)` fallback. The watchdog cannot tell that from a
crash (recurring pattern #1: a verdict made from information that doesn't support it). The
process had already *decided* to exit, but that decision was never recorded anywhere.

Fix: the marker has a third state.
- `ExitMarker` (new): `EXITING:<utc>|<reason>` alongside the existing ISO-timestamp (running)
  and `CRASH:` (watchdog) states, plus `ClassifyForWatchdog` → `Clean | IntendedExit | Unclean`.
- `App.MarkExiting(reason)` rewrites the marker **before any teardown**. It runs at the top of
  `OnExit`, in a new `OnSessionEnding` override (Windows restart/logoff) and at the start of
  the tray Exit command (before its 5s unmount wait and 3s forced exit). It writes only if
  this instance owns the marker, so utility/second instances still can't touch production
  state, and it writes at most once.
- Watchdog: on `IntendedExit` it logs INF and **does not restart** (WRN, still no restart,
  if the event log shows teardown itself crashed). It leaves the marker for startup
  diagnostics, because the OS usually kills the watchdog too.
- `PreviousSessionDiagnostics`: an `EXITING:` marker reports at Information ("previous session
  was shutting down (…) and ended before teardown finished — not a crash"), returns
  *not unclean*, so there's no balloon. A plain running marker or `CRASH:` behaves exactly as
  before, and so does an unreadable marker (still restarted, as the safe default).

## Defect 2 — the per-transfer ceiling charged a file for time it spent queued

Evidence: five consecutive relays of one 2160p release were logged as
`timed out after 133–149s … ceiling 180s`. Each timeout landed ~135 s after the previous
one. Each queued file's 180 s clock had started when it was *dispatched*, while it still
waited ~30–47 s behind the running transfer for the server gates.

Root cause: `SpreadJob` armed `CancelAfter(TransferCeiling)` in the dispatching `Task.Run`.
`ExecuteTransfer` then waits on the per-server gates (45 s each) and the pool borrow (30 s),
all of them already bounded on their own. The protocol therefore got 180 s *minus queue time*
(as little as 60 s in the worst case). The warning measured elapsed time from protocol start,
so its two numbers contradicted each other.

Fix: the dispatch-time ceiling still bounds setup, and `ExecuteTransfer` **re-arms the same
token source** (`CancelAfter` reschedules) at the moment the protocol clock (`startTime`)
starts. The transfer gets its full ceiling, and the logged elapsed time and the ceiling now
measure the same interval. Worst-case slot occupancy grows from 180 s to setup + 180 s; setup
is still bounded by the gate and borrow timeouts.

What it does **not** fix: the five timeouts themselves. Throughput on the relay path fell to
0.2–0.75 MB/s between 15:07 and 15:19 and recovered by itself, and at that rate 550 MB doesn't
fit in 180 s either way. The race completed at 15:27. See "Remaining risks".

  Restore the configured endpoint's availability or confirm its address, firewall

  The application's capped remount backoff remains active.
