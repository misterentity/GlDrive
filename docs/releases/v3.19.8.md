# GL Drive v3.19.8

This release completes the ioFTPD data-connection fix that v3.19.7 started.

v3.19.7 correctly detected that the **sitea** site (ioFTPD) stays the TLS server on CPSV data connections. It then answered as a TLS client using Windows' built-in TLS (SChannel). In production, ioFTPD reset all three of those handshakes, while OpenSSL clients and GL Drive's own GnuTLS control connection to the same server succeeded. The site went from a 10-second timeout per listing to a 3-second reset per listing, and was still unusable.

CPSV offers no benefit on a server that stays the TLS server. GL Drive now switches such a site to **standard PASV data connections**, where FluentFTP's GnuTLS client starts TLS — the arrangement ioFTPD expects, and the same TLS stack its control channel already uses successfully. FXP mode selection for the site follows the same setting.

Guards against misclassifying a glftpd site:

- A site or data address that has completed a glftpd-style handshake is never reclassified. A stalled data connection there still waits the full 10-second deadline, as in v3.19.6.
- A site without that history must show **two consecutive** data connections without a TLS hello before it is switched.
- A switch lasts six hours. After that, GL Drive tries CPSV again, so a wrong switch cannot become permanent.

The SChannel TLS-client path from v3.19.7 has been removed. The AI Setup retired-model fix from v3.19.7 is unchanged.

Validation and deployment details are in the [deployment report](https://github.com/misterentity/GlDrive/blob/master/docs/releases/v3.19.8-deployment.md).
