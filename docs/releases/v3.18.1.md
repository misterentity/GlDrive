# GL Drive v3.18.1

Two fixes from a production log sweep of v3.17.1 (2026-10-27/28). There were 0 ERR and 0 FTL lines. Both defects showed up only as INF volume.

- **Zipscript status links are no longer reported as new releases.** zephyr's zipscript places `[incomplete]-<release>`, `(no-sfv)-<release>` and `[no-nfo]-<release>` symlinks beside each release in a section. `NewReleaseMonitor` took every directory or link it listed as a release. That was 62 of the 309 unique "New release" events in the retained logs. Each one stored a duplicate notification, added a DETECTED feed row, made an auto-race attempt and ran the wishlist matcher against a symlink path. The filter checks the defining property of the whole class (a release name starts with a letter or digit; zipscript decorations, dot metadata and `-MISSING` stubs start with punctuation). It does not list the tags seen so far, so other indicators are also covered.
- **A failed direct-FXP route now stays on Relay across restarts.** Relay mode first tries direct CPSV-PASV. If that fails, both connections are poisoned (two fresh logins) and the route is remembered for 6 h. That memory existed only in RAM, so each auto-update or watchdog restart probed again. superbnc->zephyr failed 10 out of 10 times on 2026-10-27/28 (`STOR 425 Can't open data connection (timeout)` after a 15 s wait). The memory is now saved in `%AppData%\GlDrive\fxp-relay-routes.json`. The 6 h re-probe TTL is unchanged, so a route that recovers is still found. If the file can't be read, the app starts with no saved routes and probes once; it never locks a route out.

Earlier defects seen in the same window had already been fixed and have not come back: the 3.14.0 remount storm with a negative backoff (fixed in 3.15.1), and the 3.15.1 pathless source hints that failed resumed races (fixed in 3.15.2).

## Release tooling

- **The native smoke harness (`tools/ReleaseCheck`) builds again.** v3.18.0 made `CertificateManager.TrustCertificate` internal, removed the `CertificatePrompt` event (a changed pin now fails closed into a pending local decision) and added a parameter to `ServerEditDialog.AttachTofuValidation`. The harness stopped compiling, so v3.18.0 shipped without its native FTPS/WinFsp and CPSV-sharing smoke runs. The harness now has internals access, as the unit-test project does. It calls `AttachTofuValidation` directly instead of by reflection, so the next signature change breaks the harness build instead of failing at run time. The shipped app's behaviour is unchanged.

- `NewReleaseMonitorRecoveryTests`: marker links next to a new release produce exactly one event.
- `FxpRelayRouteMemoryTests`: the verdict survives a restart and still expires at the TTL, a direct success is persisted as forgetting the route, and a torn file starts empty.
- Every guard was mutation-verified. Each of the four mutants failed its tests.
- Full solution: build succeeded with 0 warnings (`TreatWarningsAsErrors`); 5,087 of 5,087 tests passed (GlDrive.Tests 5,003, Core 64, Mcp 20).
