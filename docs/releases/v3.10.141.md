## Root cause

The 17:32:25 warning asserted the 180-second per-transfer ceiling had fired, but
its own counters said 11 seconds elapsed and 0 bytes moved (recurring pattern #1:
the verdict contradicts the counters).

`CpsvDataHelper.OpenDataTcp` and `NegotiateDataTls` bound the data-channel TCP
connect and TLS handshake at 10 s each using a linked `CancellationTokenSource`.
When that private deadline expired it escaped as `OperationCanceledException`,
which every caller interprets as "my caller cancelled me":

- **SpreadJob** — any OCE after protocol start is logged as the transfer
  ceiling (`FXP transfer timed out … ceiling 180s`).
- **FxpTransfer** — telemetry row recorded `AbortReason="cancelled"` with no
  error message, so the AI digests saw a ceiling hit instead of a data-channel
  stall. A direct CPSV-PASV probe that stalled aborted the file instead of
  falling back to Relay.
- **DownloadManager** — every OCE maps to `DownloadStatus.Cancelled`; a CPSV
  download whose data channel stalled would be marked user-cancelled with **no
  retry**. Latent (no occurrence in retained telemetry), but a silent loss.
- **Spread scan** had already compensated locally in v3.10.116 by re-wrapping
  that OCE — the invariant lived in one caller's catch (recurring pattern #10).

## Fix

The deadline now belongs to the resource. `CpsvDataHelper.WithDataDeadline`
runs each setup step under its own deadline and converts *its own* expiry into
`DataChannelTimeoutException` (an `IOException`, message e.g. `data channel TLS
handshake not completed within 10s`). The caller's token still produces a
genuine cancellation. Consequences:

- FXP: logged as an ordinary transfer failure with the real cause; both
  sessions poisoned (unattributed fault ⇒ both, correct for an in-flight
  RETR/STOR); per-pair failure counted; telemetry carries the error. A stalled
  direct probe now falls back to Relay.
- Downloads: enters the normal retry-with-backoff path.
- Scan: caught by the existing non-clean `IOException` branch (poison + wrap),
  same outcome as before.

Files: `Ftp/CpsvDataHelper.cs`, new `Ftp/DataChannelTimeoutException.cs`,
comment updates in `Spread/SpreadJob.cs` and `Spread/ScanFailureClassifier.cs`.

### Remaining operational conditions and limits

- **SYN:** a fresh five-second TCP probe times out before authentication.
  Restore the endpoint/network route or obtain a corrected endpoint from its
  operator. The probe cannot distinguish a remote outage from firewall/routing
  causes.
- **T:** the remembered mapping is unavailable (`1201`), and reading its share
  returns `ERROR_BAD_NETPATH` (`53`). The host resolves, but TCP port 445 fails
  before SMB authentication. Restore the SMB host/share's reachability, then
  reconnect the existing mapping. This pass does **not** establish a credential
  failure; credentials and mappings were not changed.
- **D:** **16.056 GiB available** versus **22.565 GiB** required by the parked
  archive preflight including the reserve: **6.509 GiB additional space** is
  needed just to meet that threshold. Expanded content or concurrent writers
  may need more. Free space or select a larger extraction destination; no user
  data was removed or relocated.
- The race queue remains in memory. A future rollout must wait for an empty
  queue or preserve and restore pending work; a transfer boundary alone does
  not protect queued races.
- No live private CPSV setup timeout has recurred on v3.10.141, so the six
  deterministic regression tests establish the fix's behavior. The loopback
  harness does not reproduce a remote BNC's CPSV implementation. WPF rendering
  does not cover every interactive action, Plex authentication or external
  Upcoming data. A short health observation is not an extended soak.
