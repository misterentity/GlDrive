# v3.10.145 — keep unavailable win rates out of automatic upload-role decisions

## Production finding

The October 5 deployment of v3.10.144 exposed an erroneous AI configuration
change persisted on October 4. Zephyr's `downloadOnly` flag had changed from
false to true. The running process continued using its older configuration,
but restart activated the saved change. Both reachable servers then prohibited
receiving files, and eight queued requests failed with the specific
no-eligible-destination/download-only diagnostic.

The audit entry records the AI's rationale as a zero-percent win rate and no
successful uploads. That conclusion was false: race telemetry did not report a
winner at all, and 202 of 206 reviewed outcomes showed successful destination
delivery. `Winner = null` had been counted as a loss in race and section activity
digests. The upload-role validator accepted the boolean without establishing
that disabling uploads was justified.

## Changes

- Unknown winners no longer become losses or a zero-percent win rate. Race and
  section activity summaries distinguish known winner observations from
  unavailable data, including legacy rollups.
- Destination delivery observations provide separate evidence of useful work;
  delivery does not imply winning a competitive race.
- Autonomous configuration runs cannot change `downloadOnly`. They use the
  existing `requires-manual-action` guard; dry-run suggestions and explicit
  manual review remain available. A model confidence score is insufficient to
  change upload eligibility.
- Includes v3.10.144's queue-admission, final race-count and torrent metadata
  lifecycle fixes. See its [release report](v3.10.144.md) for their root causes
  and original validation.

## Operational recovery

At **17:36:48 UTC**, the idle v3.10.144 process was shut down cleanly. Restricted
local backups were taken, the existing validator authorized the exact
`downloadOnly: true -> false` rollback, and only that configuration field was
changed. Audit entry `055c638cb0cb40968a37c9c9d7274937` was marked undone.
The download-only target was frozen; the existing section-mapping freeze was
preserved. Credentials, mappings and user content were not changed.

The installed v3.10.144 application relaunched outside job objects as PID 82912.
Seven API smoke checks passed. At **17:37:50 UTC**, the eight independently
identified failed requests were reissued through the control API. Each was
verified exactly once in the durable queue: one active and seven waiting.
The recovery list excludes subsequent successful and already-present outcomes.
At **17:38:33 UTC**, two files had completed, both FTP servers were connected,
all eight requests remained represented, and no new job failure, Error or Fatal
record had occurred. This established actual delivery recovery before the
follow-up binary deployment.
