Debug and Information leads that were investigated and found to be correct behaviour:

- **315 `Gate timeout … ServerGate 'a8a08694' (limit=1)`** (17:00–20:00). zephyr's
  transfer gate is capped at the login gate's `Reserved` = 1 (`loginCap 4`,
  `loginHeadroom 2`). The race over-dispatches up to `maxUploadSlots` transfers
  and the extras re-queue every 45 seconds. Gate permits are taken before any
  pool borrow, so no logins are held while waiting. This is queueing, not a leak:
  the gate stayed busy (hour 18 had 3,165 of 3,600 seconds of transfer time).
- **Slow races in hours 17–19.** Per-transfer relay speed off superbnc ranged from
  0.32 to 16.6 MB/s within single releases (250 MB volumes took 24 s to 257 s).
  No local downloads were running and nothing else competed for bandwidth. The
  bottleneck was source-side.
- **`Relay complete: src=226, dst=426`** (656 times). glftpd's normal
  `426 Data Connection: Success.` on a relay STOR close. The code already reads
  this reply without validating it.
- **5 × `Failed to parse SFV`** were all `OperationCanceledException` from the
  15-second SFV read budget or race completion, not parse failures. Every
  affected race completed.
- **Race history oddities.** Three entries looked wrong:
  - `Boston.Blue.S02E03.1080p` recorded 0 delivered because zephyr was a
    co-source in that race (`altruist` was uploading to it).
  - `Elsbeth…CAKES.2` was already present on every receiving site.
  - `Gogglebox`, `Last.Leg` and others moved 0 bytes because every file was a
    dupe-skip.

  All three are correct.

## Races stopped at the 30-minute ceiling

2 of the last 500 races ended `Stopped`. Both were today's slow superbnc releases:

| Release | Delivered | Note |
|---|---|---|
| Big.Brother.UK.S23E36.Live.Eviction.1080p.HDTV.H264-DARKFLiX | 10/20 | Source delivered about 1 file per 3–8 minutes. Left incomplete on zephyr. |
| The.Celebrity.Traitors.S02E08.1080p.HDTV.H264-DARKFLiX | 15/15 | The last file landed 1 second before the ceiling. Recorded as Stopped / `1 pending` even though delivery finished. |

The ceiling is `hardTimeoutSeconds` (1200) plus `destinationCompletionWaitMinutes`
× 60 (600), which comes to 1800 seconds. It applies even to a race that is still
delivering. With `maxConcurrentRaces: 1`, removing or extending it would hold up
the queue: Celebrity Traitors had already waited 83 minutes in the queue.
Whether a race should be allowed to run past the ceiling is a policy decision
for Dave, not a defect. The Stopped-after-full-delivery label happened once in
500 races and is left as-is.

## Remaining risks

- The SYN FTP host is still down (external). About 98 mount retries a day are
  logged as expected.
- Races are throughput-bound on superbnc's per-connection speed with a single
  zephyr transfer slot (`loginHeadroom: 2`). On slow-source evenings the queue
  backs up (the oldest queued race was 1 h 50 min old at review time). A
  release that outlasts the 30-minute ceiling is left incomplete on zephyr and
  is not resumed. Tuning `loginHeadroom`, `hardTimeoutSeconds` or
  `maxConcurrentRaces` is a config decision for Dave.
- `logging.level` is still Verbose: about 40 MB per 4 hours, so the 24-file
  retention holds less than a day of history.
