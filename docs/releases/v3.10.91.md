# GlDrive v3.10.91 release record

## Findings and root causes

- Production deployment of v3.10.90 completed its download, RSA checksum-signature validation,
  SHA-256 archive validation, and SYSTEM-task hand-off, but the task returned before consuming
  the pending request. The v3.10.89 installation remained intact.
- Root cause: both updater modes were routed through `App.OnStartup`. The SYSTEM task runs in a
  non-interactive session, where WPF application startup can end before `OnStartup` executes.
  The custom executable entry point already existed, but it constructed WPF before dispatching
  the updater.

## Changes

- Dispatch `--apply-update-task` in `Program.Main` before constructing the WPF application.
- Dispatch the legacy interactive `--apply-update` path at the same headless boundary.
- Retain the existing fixed task action, signed package verification, HMAC-bound manifest,
  rollback, and relaunch behavior.
- Add a regression test that requires both updater dispatches to precede WPF construction and
  prevents them from moving back into `App.OnStartup`.
- Include the v3.10.90 atomic updater-key initialization fix unchanged.

## Validation

Pending final build, regression, package smoke, CI, deployment, and production health results.

## Release

Version: **3.10.91**

Published from commit `447c4d1dff65b6eab75ea5965e80acc305fc0d54`. Installer bootstrap confirmed
the headless entry point, but live SYSTEM-task validation exposed two further boundary defects:
task mode required a CurrentUser-DPAPI authorization marker that SYSTEM cannot resolve, and the
handoff cleanup sat in a `finally` after an applicator that intentionally terminates its process.
This release was superseded by v3.10.93.

## Remaining risks

- SYN remains externally unreachable; GlDrive's bounded remount loop continues to handle it.
- Remote FXP endpoints can still refuse transient data connections; observed failures recovered
  on retry, so no application change was warranted.
