# v3.10.148 — Relay transfer ceiling measures inactivity, not wall time

## Log review and root causes

Reviewed the retained application logs (October 4–6, 2026; 24,401 records), Windows
Application `.NET Runtime` crash events, the installed process, heartbeat and release
identity. Baseline was v3.10.147, PID 98916. Local log timestamps are UTC−07:00.

There were **zero Error/Fatal records and zero native-crash events**. Every watchdog line was
a clean update relaunch. Warnings, grouped by cause:

| --- | ---: | --- |
| T: download destination not mounted | ~120 | External — downloads parked safely. |
| SYN mount/remount timeout | ~65 | External — FTP host unreachable since 2026-08-13. |

### Defect: wall-clock ceiling killed healthy Relay transfers

All 13 timeout warnings were superbnc → zephyr **Relay** transfers that were **still moving
data** at about 2.4 MB/s when the 180s per-transfer ceiling (3 × `TransferTimeoutSeconds`)
fired:

- 2026-10-04: `the.last.drive.in…r09` cut off at **496,910,336 of 500,000,000 bytes (99.4%)**.
- 2026-10-06 18:03–18:53: nine Ted.Lasso S04E10 volumes (650–700 MB each) cut off at
  230–664 MB. Each one was poisoned, both logins were discarded, and the volume was sent
  again from zero.

The ceiling was a wall clock. A 650 MB volume at the route's real speed needs about 270s, so
it could **never** finish within 180s. Races only completed because some retries happened to
run faster, or because another racer supplied the file. The cost was about 3.5 GB of
redundant relay traffic and roughly 30 minutes of race-queue time in one evening.
`FxpTransfer`'s own relay deadline (20 × the timeout, 1200s) was already sized for large
volumes, but the outer ceiling overrode it. This is the "bounded on DURATION when the
question was ACTIVITY" pattern (see v3.10.73).

## Changes

- Relay progress events now re-arm the per-transfer ceiling, throttled to once per second.
  For Relay, the ceiling is now a **180s no-progress window**. Total duration is still capped
  by FxpTransfer's relay deadline.
- The re-arm is keyed on the progress event itself, not on the detected mode, so a CPSV-PASV
  transfer that falls back to Relay mid-call is covered too. Server-to-server modes report
  no progress and keep the wall-clock ceiling.
- The timeout warning now reads `no progress for 180s` when that is what fired, instead of
  `ceiling 180s` next to an elapsed time that exceeds it.
- Widened the timer margins in `CancelAfter_rearm_replaces_the_pending_deadline` (150ms
  timer vs a 100ms delay). It failed the first `release.ps1` run under release-build load,
  before anything was published. The new behavioural test uses the same wide margins.

## Remaining risks

- **The fix is not yet proven on a live slow relay.** No Relay transfer longer than 180s
  happened in the observation window. Confirm on the next large superbnc → zephyr race:
  `FXP transfer timed out` should disappear, or read `no progress for 180s` with a static
  byte count.
- A relay that trickles bytes slowly now runs up to FxpTransfer's 1200s relay deadline
  instead of 180s. That is intended, but a degraded route can now hold a slot longer.
- Direct (server-to-server) modes still use the 180s wall-clock ceiling, because they report
  no progress. No timeouts in those modes were observed in the logs.
- External items, unchanged: T: is not mounted (downloads parked); the SYN FTP host is
  unreachable; PreDB and OpenRouter have intermittent upstream timeouts and 429s.
