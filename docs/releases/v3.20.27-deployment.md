# GL Drive v3.20.27 deployment review

## Application change

Release commit `3f8715d2d3459349f6a699e646411e2df32e045d` gives the site-statistics probe ten seconds after a pool connection becomes available. Previously the queue wait consumed the probe deadline. A loopback regression held the only lease for six seconds and delayed the SITE reply for six more. The old build returned null credits. The fixed build returned the expected 42 GB and kept the session usable. All four deadline tests passed, including a saturated pool, a stalled command and a disconnected peer. A single refresh can now take approximately twenty seconds across both phases.

## Installed smoke and observation

The updated site-statistics operation returned fresh credits for the affected site in about 1.1 seconds. The 64 installed WPF screens passed the same checks as the candidate, and the installed application DLL matched the one used in the native fixture. At first one enabled IRC connection was still starting and its status query returned HTTP 409. It reconnected without intervention. The repeated smoke passed four FTP root listings and all three enabled IRC checks. The 163 application records between the baseline cutoff and the start of monitoring were informational. The matching Windows Application event count was zero.

Monitoring ran for 10 minutes 32 seconds, from 16:19:14 to 16:29:45 UTC. The process ID stayed stable. The first health sample captured the IRC startup delay and all 14 subsequent samples passed. Log-retention verification passed. Of 103 application records, 101 were informational and two were warnings. There were zero Error or Fatal records and zero matching Windows Application events.

The strict rollout monitor returned a failed aggregate verdict. In addition to the first IRC sample, two spread jobs failed because the destination refused to create the requested directories. The server explicitly reported that directory creation was disallowed. One rejection also caused the direct transfer route to stay on relay for a six-hour retry interval. The site owner must confirm whether the destination policy or mapping should change. Both refusals are included in the observation result.

The six announce-channel configuration warnings still need confirmed channel mappings. The two historical inactivity stops have no conclusive underlying cause in the retained logs. The previously failed download needs a valid source. External provider availability, connection timeouts, and content relocation remain operational risks. Validation covers the observed Windows installation and time window. No live rollback was performed.

The local readiness helper now preserves UTC when PowerShell deserializes a timestamp as a DateTime. The corrected timestamp calculation passed in both Windows PowerShell and PowerShell 7.
