## Finding and root cause

**The race's file set was add-only, so a file the source listed once and deleted seconds
later stayed "missing" for the rest of the race.**

- 04:20:45 — the source listing for the E44 release went 27 → 28 files. The 28th was
  `masterchef.australia.s18e45…r01`: an **E45** volume in the **E44** directory (a wrong-dir
  upload; the site's zipscript removed it within seconds).
- 04:21:08 onward — 25 consecutive source listings said 27 again, while `FindBestTransfer`
  kept saying "28 files" and the completion check kept saying "1 files still missing".
- `SpreadJob._fileInfos` / `_fileOwnership` had **no removal site anywhere**;
  `FileOwnershipReconciler.Observe` only ever added.
- The RETR-550 handler called `HandleSourceMigration`, which re-probes whether the release
  **directory** still exists — it does — and logged "transient, not migrating" 27 times. It never
  asked whether the **file** was still listed.
- The completion sweep then did exactly what it is for — cleared failures and `Reinitialize`d
  every pool — five times at 65 s intervals. Each reinit re-logged into the BNC at the login
  cap, produced `Pool exhausted`, and triggered a ghost-kill (correctly 60 s apart under the
  v3.10.105 throttle) that severed live sessions.
- After `MaxNoProgressSweeps` the race declared partial 27/28 and ran `SITE WIPE -r` on the
  destination, which held all 27 real files. Total cost: 56 `RETR 550`, 10 minutes, one good
  release wiped, and E45 held in the queue behind it.

## Changes

- `FileOwnershipReconciler.Prune(serverId, listing, …)` applies the negative half of a
  listing: a site that owned a file and no longer lists it loses that ownership; a file with no
  owners left leaves the set. Dropped names are returned and logged (`… no longer lists N
  file(s) … dropped from the race set`).
- An **empty** listing prunes nothing — glftpd moves a finished release between sections,
  which reads as "0 files" for one cycle and is handled by the relocation follower.
- `SpreadJob.ProcessFiles` calls `Prune` after applying each listing, under `if (!_isNuked)`,
  because a nuke marker aborts the directory walk mid-way and returns a partial list. Dropped
  names are also removed from `_fileActions`.
- The ghost-kill log line still said "(once per episode)" after v3.10.105 replaced that logic;
  it now names the per-account 60 s throttle.

## Remaining risks

- **The new prune path has not fired in production yet.** It only acts when a site's listing
  drops a file it previously listed, which happened once in three days of logs. Watch for the
  INF line `no longer lists N file(s) … dropped from the race set` and confirm each occurrence
  names a file the site genuinely removed, not one that a partial or wrong-path listing missed.
  The guards against that (empty listing, nuke abort, LIST-failure throws) are unit-tested and
  mutation-verified but have only the design behind them under live load.
- **A false drop would look like a false "complete".** If a source ever returns a truncated but
  non-empty listing, files would be revoked and a destination could read complete early. The
  scan path throws on any LIST error rather than returning partial results, so this needs a
  new failure mode to occur; still, a race that completes with fewer files than its SFV declares
  is the signature to look for (`ResolveFileTotal` keeps the SFV count as a floor, which bounds
  this).
- The completion sweep still reinitialises every pool on each pass. With the phantom case
  removed that is back to its intended transient-failure role, but it remains the most
  login-expensive action in the race loop.
- SYN's FTP endpoint remains down (three remount WRNs in the first four minutes);
  `loginHeadroom: 2` still caps FXP at one transfer per site. Both are Dave's, not code.
- Working-set trend on v3.10.106/.107 needs the 24 h and 48 h samples the previous record asked
  for; 319 MB at 20 h is encouraging but not a verdict.
