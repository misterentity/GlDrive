# GL Drive v3.11.27

Direct FXP transfers now require successful completion replies from both servers
before they are reported as delivered. Previously, an unexpected source or
destination reply was logged as a warning but the transfer was still marked
complete. This could incorrectly credit destination ownership and suppress a
needed retry.

The fix retains the shared completion deadline, drains received replies before
validating them, preserves cancellation, and keeps conservative connection
quarantine on failure. Rejected completions and timed-out direct probes record
the failed route and return their connections for quarantine; the next attempt
can use relay with fresh connections. They do not send relay commands on the
failed sessions or record the route as successful. Relay transfers keep their existing byte-count verification and
handling of glftpd's `426 Data Connection: Success.` response.

This defect was found during code review, not as the cause of the seven transfer
failures in the audited production run. All seven later completed through normal
retry or source relocation. The current run had no Error/Fatal events or new
crash reports. External service availability and finite observation limits are
recorded separately from the code fix.

Build, regression, smoke, release provenance and production observation results
are recorded in the [deployment report](https://github.com/misterentity/GlDrive/blob/master/docs/releases/v3.11.27-deployment.md).
