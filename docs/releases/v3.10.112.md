# GlDrive v3.10.112

Log sweep of 2026-09-07 → 09-09 (v3.10.107 → v3.10.110 in production). Three days, 112,749 log lines, **0 ERR / 0 FTL**; WRN volume fell 115 → 65 → 32 per day, FXP completions 1,587 / 2,142 / 1,515, races completed 150 / 208 / 150, borrow timeouts 0. The only defect class still costing logins was invisible at the error level: healthy CPSV connections were being discarded after a clean command rejection.

## Fixes

- **A final negative reply to a CPSV data command no longer quarantines the connection.** `CpsvDataHelper` marks a control channel as "owing a reply" before `LIST` / `RETR` / `STOR` is sent, and only a successful completion read cleared it. When the server rejected the data command itself with a final 4xx/5xx (`LIST 550 No such file`, `RETR 550` after the source moved a release, `STOR 425 Can't build data connection`) no transfer had begun and no `226` would follow — the channel was in sync — yet the mark stayed set and the pool discarded the connection on return. The new `RejectDataCommand` helper clears the mark for final negative replies and throws a typed `DataCommandRejectedException`; a `421` (session closing) or a non-negative code (a stale reply, the desync signature) keeps the mark. All five throw sites route through it, pinned by a structural test.
- **Relay RETR rejection now entangles neither side.** v3.10.110 preserved the destination after a rejected `RETR`; the source was still poisoned. A source that answers `550` has closed its data socket and owes nothing, so the new `FxpFaultSide.Neither` attribution spends no login. Production tell: 2026-09-08 03:02, three `RETR 550` replies in ten seconds cost six logins against a 4-login cap and cascaded into ghost-kills, a 90 s BNC cooldown and four `Pool exhausted` transfer errors before the race recovered.
- **Callers that poison on failure now exempt clean rejections.** `FtpOperations` (listing, download, upload, stream download) and the `SpreadJob` scan listing each wrapped a CPSV call in a catch that poisoned the borrowed connection unconditionally. Transport faults, timeouts and cancellation still poison.
- **The search-index crawl no longer aborts a whole search root on one failed listing, and reports what it lost.** Every hourly build discarded exactly two connections (39 of the 102 poisoned-discards on 09-09 were adjacent to the 23 `Search index built` lines) and the cause was logged at Debug against an Information sink. A failed subdirectory now costs only its own subtree; the build line reports `N directory listing(s) failed, first <path>: <error>` so the next sweep can read the cause.
