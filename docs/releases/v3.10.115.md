# GlDrive v3.10.115

## Findings and fixes

Reviewed all three retained daily application logs on 2026-09-11 through approximately 09:02 PT: September 9 (34,355 lines, 41 warnings), September 10 (67,940 lines, 83 warnings), and September 11 (20,002 lines, 23 warnings). No Error or Fatal entries appeared in that snapshot. This does not mean all operations succeeded: failed transfers, directory listings, and reconnects also appear at Warning and Information.

The September 11 00:55:46 connection-loss warning omitted both the server and the failure reason. Adjacent pool/UI lines identify the affected server; a reconnect completed at 00:55:54. The historical log cannot distinguish a NOOP timeout from a transport exception. Inspecting that path revealed these application defects:

- `ConnectionMonitor` awaited `Execute("NOOP")` and unconditionally declared success. FluentFTP returns rejected FTP replies normally, so a 421/450/500/530 rejection could be reported as healthy. A probe now requires a positive completion reply, preserves the FTP failure code, and quarantines the connection on failure.
- Reconnect reported success immediately after `Initialize`, which can return without connecting when the pool already contains a connection. Recovery now requires a successful probe too.
- Catch-all handlers swallowed shutdown cancellation and could report connection loss during shutdown. Cancellation now propagates without a disconnect/reconnect event. A cancelled or timed-out managed wait still poisons the connection and observes the outstanding task; the native GnuTLS read remains non-cancellable and uses the existing deferred cleanup.
- Connection-monitor diagnostics now include the server and the reason for loss. This closes the evidence gap without claiming the new reply-validation defect caused the historical timeout.

The disposable native FTPS fixture now supports two deliberate NOOP rejections, covering both initial failure and a failed recovery probe. Version references and the deployment guide were refreshed.

The first CI run (34620455506, commit 37ab01b) then caught an intermittent failure in the existing randomized DH1080/CBC round-trip test. Investigation reproduced a decoder defect with fixed exponent 6402: its public key ends in twelve zero bits, and stripping repeated trailing base64 `A` characters drops a significant byte. The peers derive different shared secrets, breaking both ECB and CBC messages. Six deterministic regression cases failed before the fix. Decoding now removes only the length-identified FiSH flush marker and preserves significant zero bytes. Twelve new cases cover shared-secret agreement, message round-trips, and fixed/variable-width keys with standard, unpadded, and FiSH encodings. Existing independent interop vectors pass. The original CI run did not record its random keys, so its exact input cannot be replayed.

Protocol reference: [FiSH-irssi encoder/decoder source](https://github.com/falsovsky/FiSH-irssi/blob/master/src/base64.c). Its encoder emits an extra flush character for three-byte-aligned input; reproducing a legacy decoder's zero-stripping behavior is not sufficient to preserve the original public integer.

## Remaining external failures and risks

- SYN FTP remains unreachable; retries hit the approximately 21-second connection deadline. Resolving this requires the server/network owner to restore the endpoint or provide corrected connection details. No server configuration was changed to hide the failure.
- zephyr continues returning `425 Can't build data connection: Connection refused` during LIST/STOR and some transfers. September 11 hourly partial indexes retained approximately 6,995 entries while reporting 17–18 failed listings in the sampled later hours. The reply establishes failure of the remote data connection; exact server/firewall cause cannot be proven without server-side logs/access. Search coverage remains incomplete.
- Source-side moves from incoming to recent explain observed RETR 550 failures; existing relocation handling follows the moved release. Remote control stalls and transport resets remain possible. The September 10 GnuTLS drain warning deliberately retained an unsafe-to-free native session rather than crashing.
- The v3.10.114 direct-route re-probe diagnostic appeared at 06:06 on September 11, followed by the two named quarantines expected for fallback to Relay. That behavior is confirmed, not a new failure introduced by this release.
- September 10 PreDB HTTP timeouts were transient and backed off. The application cannot guarantee availability of its remote dependencies.
- No extended remote BNC soak or fleet-wide telemetry is available. Production verification covers this installed Windows instance, its local control API, logs, heartbeat, and observed activity. Recovery adds one bounded NOOP round trip. Roll back through the prior v3.10.114 installer if a regression is confirmed; user data is preserved by the installer.
- Legacy peers that themselves discard significant DH1080 zero bits can still require a fresh key exchange; this release fixes GL Drive's decoder without changing the outgoing wire format. No live private messages were sent for validation.
- The disposable FTPS fixture process was stopped. Automatic approval review rejected deleting its temporary directory (reason: "blocked by policy"); temporary fixture files remain under `%TEMP%\gldrive-ftps-check-s21_722n`.
