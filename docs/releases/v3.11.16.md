### 1. SITE INVITE starved behind a one-connection main pool

One site's account allows four logins; with headroom and the FXP reservation, its main pool
holds **one** connection. Spread scans keep that connection busy about 145 times an hour,
which is normal and already handled by a scan fallback. SITE INVITE borrowed only from
the main pool, waited its full 30 s budget, then timed out. The site's announce channels
stay invite-only until the next standing retry 5–15 minutes later. On 10-15 this happened
7 times, including one continuous 65-minute window with no announces from that site.

The invite now waits 10 s for the main pool, then sends on the server's live spread
pool (`Ftp/PoolFallback`, `SpreadManager.GetLivePool`). It is one control command held for
under a second. The fallback is logged at INF: `main FTP pool busy — sending SITE INVITE on the spread pool`.

### 2. Extractor replayed a release that was incomplete at its source

A release folder that was downloaded while the source held 20% of it contained the site's zipscript stubs
(`*.rNN-missing`, `[##] - 20% Complete - …`), along with 3 of its 15 parts. A later release
already stops downloads from bringing these stubs to disk. The folder already on disk was never
going to complete. Even so, every process start replayed six 300 s readiness waits and 13 WRN lines against it.
This was the top WRN class on both 10-14 and 10-15.

Both readiness routes now share `HandleStalledArchive`. When a stalled set is missing parts **and**
its folder contains a source incomplete marker (`ReleaseSourceState.FindIncompleteMarker`),
the path is abandoned durably. The verdict is keyed to the volume-set fingerprint, so it
lapses automatically when a missing part arrives. Stalls without that evidence still take
the bounded retry path unchanged.

## Remaining risks

- **Spread-pool contention:** the fallback can briefly hold the spread pool's only usable
  login. That lasts under a second, once per IRC (re)connect. An FXP borrow in that instant waits
  rather than fails.
- **Live search on a one-connection site** still returns partial results while scans hold
  the main pool. This is capacity, not a defect. Raising the login cap or lowering headroom is a configuration decision.
- **Durable verdicts are keyed by fingerprint:** a copy that later adds parts revives the path. If a user
  manually replaces the stub files without changing any part, the verdict stays until a part changes.
- **The SYN FTP host is still unreachable** (external, since 2026-08-13).
