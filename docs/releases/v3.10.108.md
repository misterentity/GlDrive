## Root causes and changes

- A successful empty source listing did not start relocation recovery; only a later RETR 550 did.
  `SpreadJob` now treats an empty listing as relocation evidence after that source previously
  supplied files, provided the scan has neither a completion marker nor a missing-release stub.
- The relocation probe was asynchronous while the scheduler continued selecting the stale source
  path. A bounded `_sourceMigrationPending` state is now set before the first probe await and makes
  that source ineligible for transfer scoring until the handler finishes.
- The generic transfer catch poisoned both pooled connections even when the second pool failed
  before the first TYPE/PASV/CPSV/STOR/RETR command. `FxpFailurePolicy` now preserves untouched
  peers before that protocol boundary. Expected pool/gate pressure is logged once at information
  level with pool diagnosis; unexpected setup faults retain warning visibility, and failures after
  protocol begins retain conservative poisoning.
- The remaining xUnit analyzer warning was removed by awaiting the concurrency test's tasks.
- Product and README versions were advanced to **3.10.108** and the changelog was updated.

## Remaining risks

- The proactive empty-list relocation branch is regression-tested but awaits its first naturally
  occurring production relocation. A small number of transfers dispatched before the empty
  listing is observed can still fail; the new pending state prevents further dispatch afterward.
- The clean-peer decision depends on `transferProtocolStarted` being set immediately before
  `FxpTransfer.ExecuteAsync`. Future transfer setup moved below that boundary must be reviewed.
- Remote `425` data-channel failures remain possible and are outside the client. All observed
  cases recovered through bounded retry.
- SYN remains enabled but unreachable at its configured endpoint, so expected remount messages
  will continue until the remote service or configuration is corrected.
- The installer is not Authenticode-signed. Auto-update still requires both the signed checksum
  manifest and a matching SHA-256 package digest.
- Working-set behavior should continue to be sampled over 24–48 hours; the v3.10.106 native TLS
  leak fix remains healthy so far, but this release's immediate smoke window is not a long-run test.
