## What this fixes

Auto-install waits for the app to be idle before installing. On this box that reliably landed at
~03:35, raised a UAC prompt with nobody at the keyboard, and let the Windows secure desktop time it
out. `ShellExecute` returns `ERROR_CANCELLED` (1223) for **both** "user clicked No" and "prompt
expired unanswered", so the app recorded a decision nobody made, suppressed the release for 24h,
and re-offered it at the same hour the next night — where it failed identically.

The correlation across four releases is total:

| Version | Auto-install started | Outcome | start → "declined" |
|---|---|---|---|
| v3.10.79 | **09:31** (daytime) | installed | — |
| v3.10.80 | **03:34** (night) | "declined" | 131s |
| v3.10.81 | **09:36** (daytime) | installed | — |
| v3.10.82 | **03:39** (night) | "declined" | 132s |

131s and 132s is download plus the **120s secure-desktop timeout**. An invariant duration across
occurrences is a structural ceiling, not a person — a human clicking "No" produces variable timing.

The cause underneath: **the idle gate selects for exactly the hours no human is present, then
requires a human to approve elevation.** The two conditions can never both hold. `UpdateChecker`'s
own comment already said so ("the auto-install prompt fires around 05:00 when nobody is at the
machine"); three releases of mitigation (v3.10.33, v3.10.41, the `ClearDeclinedUpdate` fix) all
treated consequences rather than the cause.

## Changes

- The installer registers **`GlDrive Update Installer`**: runs as SYSTEM, highest privileges,
  **no trigger at all**, action fixed to the installed executable plus `--apply-update-task`.
  The app hands off through `%ProgramData%\GlDrive\pending-update.json` and starts it with
  `schtasks /run`. A missing task falls back to the old interactive path.
- A `1223` that took ≥90s is now logged as an unanswered timeout and does **not** record a 24h
  decline. Only a genuine short cancellation does.
- **v3.10.85**: `register-update-task.ps1` is published with the app and re-run by the elevated
  updater after a successful install, so the feature bootstraps itself.

### Security model

The hand-off file is attacker-writable input to an elevated process and is treated as untrusted —
but it is deliberately **not** the security boundary:

- **It carries no install destination.** `ApplyUpdate` already requires the destination to equal
  the elevated process's *own* directory, so the destination is pinned by where the task's action
  lives (Program Files) and cannot be redirected from the hand-off.
- **It carries no code.** The package is re-verified inside the elevated process against an RSA
  public key compiled into `GlDrive.exe`, and rejected unless strictly newer than the running
  version. The verifier hashes the open stream and extracts from that same handle, so the file
  cannot be swapped between check and use.

The worst a forged hand-off achieves is pointing the updater at a *validly signed, strictly newer*
GlDrive package — which is what the updater does anyway. It still validates shape, staleness (30
min), clock skew, and refuses a directory named `Temp` because the updater deletes the package
directory recursively.

The task's ACL grants Authenticated Users read+execute (so the non-elevated app can start it);
Administrators and SYSTEM keep full control, so a standard user cannot redefine what it runs.

## Found while building, not by reasoning

- **`Program.cs` guarded `--apply-update` with `Array.IndexOf`, an exact match**, so
  `--apply-update-task` would not have matched and the SYSTEM task's process would have spawned a
  watchdog and raced its own file replacement. The existing test sliced a **fixed 180-char window**
  and failed on width rather than on the property under test; it now runs to the `SpawnWatchdog()`
  call and asserts all three exclusions.
- **`schtasks /create` requires a schedule, and its `/sd` format is locale-dependent** —
  `01/01/2099` is rejected on a machine expecting `yyyy/mm/dd`. Caught by actually running the
  command rather than trusting it. Registration moved to `Register-ScheduledTask`, which needs no
  trigger at all.
- **v3.10.84 was inert on the path that matters.** It shipped the registration script only through
  the Inno installer, but the auto-updater applies the release **zip**, which never runs that
  installer — so the task would never have been registered where it was most needed. Found by
  listing the shipped zip's contents rather than trusting the `.iss` change. v3.10.85 fixes it and
  adds a guard that fails if the script stops shipping.

## Remaining risks

- **One manual install is still required, and this is the important one.** The box runs 3.10.81,
  which contains none of this work: it will offer v3.10.85, prompt at ~03:35, time out, and record
  a decline exactly as before. **Install v3.10.85 by hand once** (tray menu or the setup exe). After
  that the task exists and every later update is unattended.
- **Not verified end to end.** The task only exists after an elevated install, so the first real
  unattended update is the true proof. Everything up to that point — quoting, registration shape,
  hand-off validation, argument routing, shipping — is verified; the full round trip is not.
- Whether a **non-elevated** process can start the task depends on the SDDL grant applied at
  registration. It is set explicitly, but if it does not take on this machine the app degrades to
  the interactive prompt (logged, not silent) rather than failing.
- Concurrent work: another session released v3.10.83 from this repo mid-session. This work was
  rebuilt and re-tested on top of it, and its `App.xaml.cs` diff was confirmed to be **10
  insertions, 0 deletions** so nothing of theirs was reverted. Worth knowing that two agents were
  releasing from one working tree.
- SYN still down; six downloads still parked on the absent `T:` volume.
