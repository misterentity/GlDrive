## Log review and root causes

Three retained daily logs (2026-08-24/25/26) were reviewed, then narrowed to the window
after the v3.10.81 process banner at `09:39:08` on 08-26 — the earlier hours of that file
are a different build, and pooling them hides the trend.

**The headline finding is a negative one: v3.10.81 has no production errors.** Over the
9.6-hour window it logged **0 `ERR`, 0 `FTL`**, and completed **411 FXP transfers against
2 failures (99.5%)** across 33 race completions. WRN volume is trending down across the
three days (497 → 337 → 176). No code defect was found in the running build.

### What the sweep did find

v3.10.80's own stated lesson was *“when one half of a subsystem has a hard-won comment,
grep the other half.”* It fixed `LogDigester.ReadFile` (silent parse-skip) and
`TelemetryRecorder` (BOM-emitting `Encoding.UTF8`) — and left **three siblings carrying the
identical `catch { continue; }`**, plus one BOM writer:

| Defect | Impact | Severity |
|---|---|---|
| `AuditTrail.MarkUndone` rebuilt the whole file from `ReadAll()`, which had already filtered out unparseable rows — so the first undo after a torn write **erased that row permanently** | Data loss from the undo/forensics record for AI-driven `AppConfig` mutations | **Latent, destructive** |
| `AuditTrail.ReadAll` dropped unparseable rows with no log line at any level | Undo history silently incomplete | Latent |
| `SectionActivityRollup.RollUp` same silent drop — and it is the **only** producer of `SectionActivityEvent` | A dropped race under-reports that section for the whole day, steering the agent's section→folder learning | Latent |
| `NukePoller.TryCorrelateRace` same silent drop | Best-effort correlation loses rows quietly | Low |
| `AuditTrail` wrote via `Encoding.UTF8`, stamping a BOM at position 0 | Readers strip it, but any raw-byte consumer chokes on line 1 | Cosmetic |

These are **latent, not active**: `ai-audit.jsonl` parses 2548/2548 rows today and the last
five `AgentRunner` runs are `status=ok`. That is precisely the point — these failure modes
leave no trace, which is how they survived a release.

A **new recurring shape** was recorded from this: *a lossy reader wired into a whole-file
rewriter is a data shredder.* Neither half is dangerous alone.

### Verified, not assumed

Every `ai-data` file dated 08-26 still carried a BOM, which looked like a v3.10.80
regression. It was not: those files were created at midnight by the **pre-.81** build —
v3.10.80's auto-install had been **declined at the UAC prompt** at 03:36, so the host only
reached .81 at 09:39. Confirmed by reading `TelemetryRecorder.FileEncoding` in source
rather than inferring from bytes on disk.

## Changes

- `AuditTrail.MarkUndone` now reads raw lines and preserves anything it cannot parse
  **verbatim**; rows that parse but do not match are written back byte-identical rather
  than reserialized. The rewrite uses `"\n"` to match `Append` instead of
  `StringBuilder.AppendLine`'s CRLF, which previously left mixed line endings after the
  first undo.
- `AuditTrail` writes are BOM-free via the same `UTF8Encoding(false)` the v3.10.80
  `TelemetryRecorder` fix introduced.
- `AuditTrail.ReadAll` and `SectionActivityRollup.RollUp` count parse skips and report them
  at **Warning** (the Serilog sink runs at Information, so a Debug line is invisible —
  the blind spot that hid the v3.10.70 poison row for 40+ runs). Both expose a
  `ParseSkips` counter mirroring `LogDigester.ParseSkips`.
- `NukePoller.TryCorrelateRace` logs its skip instead of swallowing it.
- Rows are still skipped rather than aborting the stream — one bad row must not cost the
  whole file.

## Validation

- Baseline before changes: **1,022** tests passed.
- Final regression suite: **1,037 passed, 0 failed, 0 skipped** (+15).
- Build: `dotnet build src/GlDrive/GlDrive.csproj` — **0 errors** (10 pre-existing warnings,
  unchanged).
- **All eight new guards mutation-verified.** Three initially failed verification and were
  corrected:
  - Two mutants "passed" because heredoc escaping collapsed `\n`, so the `str.replace`
    matched nothing and the run tested unmutated source. The harness now `diff`s the file
    after mutating and skips the run if unchanged, and patterns assert `count == 1` so an
    ambiguous match (one matched **two** writers) fails loudly.
  - One mutant survived because a redundant early `ParseSkips = 0` was doing the work of
    the line under test; the counter was collapsed to a single load-bearing assignment.
- Tests are **behavioural against real files on disk** (asserting bytes and surviving rows),
  not substring assertions on source, so a rename cannot silently make them vacuous.
- Production-shaped smoke coverage (`ProductionDataSmokeTests`) over a 600-row BOM-prefixed
  audit fixture and a 150-row races fixture. Fixture presence in `bin/` was verified — both
  tests skip when the fixture is absent, and a silently-skipping test is a vacuous one.
- NuGet transitive vulnerability audit: **no known vulnerable packages**.
- GitHub CI on the release commit: **success**
  (https://github.com/misterentity/GlDrive/actions/runs/33032655608). The push trigger fired
  normally; the v3.10.81 missing-trigger caveat did not recur.

### Smoke-test scope

Changes are confined to three `AiAgent` persistence classes. The WinFsp, WPF, and live-FTP
layers are untouched by this release and were **not** re-exercised: the production instance
was mid-race throughout, and launching a second instance risks the single-instance guard and
the live mount. The published binary was verified by metadata
(`FileVersion 3.10.82.0`, `ProductVersion 3.10.82+a14c5a6…`, 1,148-file publish) and the
production process confirmed undisturbed.

## Remaining risks

- **v3.10.82 is published but not yet installed.** The host still runs 3.10.81.
  Observed (not predicted): the updater picked the release up at **21:39:40** and deferred it —
  `Update v3.10.82 ready but deferred (busy) for 0.0h — retrying next check (forced install
  after 12h)`. The blocker is the **busy gate**, not UAC: the box was mid-race, and a live FXP
  transfer legitimately suppresses an install. An earlier draft of this report named UAC as the
  likely cause because v3.10.80 was declined there on 2026-08-26; that was wrong for this release.
  - Deferral start is **persisted** to `%AppData%\GlDrive\.update-deferred`
    (`v3.10.82  2026-08-27T04:39:40Z`), so the v3.10.39 defect — the clock living in a field and
    being zeroed by every restart — does not apply. The forced install stands at **09:39 local
    on 2026-08-27**, with 3-hourly retries before it (next ~00:39).
  - It can be applied immediately from the tray menu if the wait is not wanted.
- The two `AuditTrail` defects were **latent** — no row loss has occurred yet. The fix is
  therefore unproven against a real torn write; it is proven against synthetic and
  production-shaped fixtures only.
- **SYN remains down** since 2026-08-13 (external). It continues to consume remount attempts
  and suppress races that would otherwise have a second destination.
- **Six downloads remain parked** until `T:` is mounted or their destination is changed.
  The ladder caps at hourly and retries indefinitely with no escalation path, so this
  produces ~144 warnings/day for as long as the volume is absent. Working as designed, but
  it is 83% of all warning volume and will mask a new signature in future sweeps.
- `AuditTrail.ReadAll` sets `ParseSkips` only when the enumeration is run to completion; a
  caller that breaks early leaves the count under-reported. All current callers enumerate
  fully.
- Transient remote FXP/data-channel failures will recur (2 in this window, both recovered;
  a further 1 of 128 since the deferral, also recovered).
- **The deployment watcher used during this release was itself defective** and is not evidence
  of anything beyond the log lines it echoed. Its success path compared a heartbeat version
  read via `$HOME`-interpolated Python — `$HOME` expanded to the MSYS path `/c/Users/...`,
  which Windows Python cannot open, and `2>/dev/null` hid the traceback. The variable was
  always empty, so the "deployed" branch could never fire and the run could only ever time out.
  A guard that cannot fire is inert, not conservative — the same shape as v3.10.54, self-inflicted.
