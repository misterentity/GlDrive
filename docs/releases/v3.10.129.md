### Defect fixed: the AI agent ran twice around its daily slot

`ai-briefs/` shows two runs on 09-13 (03:08 and 04:00) and 09-14 (03:08 and 04:00).
It also shows two on 09-22 (03:53 and 04:00), and on 09-20/21 (23:04, then 04:00).
The September 22 log shows the full sequence:

```
03:52:30.323 AgentRunner catch-up scheduled in 1 min   (×3, SystemEvents.TimeChanged)
03:53:30     run ddf8dc55 STARTED → finished ok
03:54:24     AgentRunner next run in 00:05:35
04:00:00     run 82d21316 STARTED → finished ok
```

Root cause: `NeedsCatchUp` treated any gap of 23 hours or more as a missed run. It
measured elapsed time instead of checking whether a scheduled slot had passed without
a run. The 09-21 run finished at 04:04. A `TimeChanged` event at 03:52 re-ran
`ScheduleNext` after 23.8 hours, so the check reported a miss even though yesterday's
slot had been served. After the catch-up run, the regular 04:00 slot ran as well.

Each extra run costs one LLM call and uses a full per-category change budget. It also
decrements `DryRunsRemaining` for no new data. The existing test
`GenuinelyMissedRun_StillTriggersCatchUp` asserted that `lastRun + 23h` must trigger a
catch-up, so the test suite enforced the bug.

## Changes

- `AgentRunner.PlanSchedule(lastRunUtc, nowUtc, runHourLocal, tz)` replaces
  `NeedsCatchUp`. Any run in the 12 hours before a slot, or after it, counts as serving
  that slot. A catch-up is scheduled only when the most recent slot is unserved. The
  next timer skips a slot a recent catch-up already served. Retry backoff after
  failures is unchanged. A slot that falls in a DST gap moves to the first valid time.
- Tests: the enforcing assertion was replaced. New cases cover the exact 09-22
  timeline, the 09-20 late catch-up, genuine misses 30 h and 67 h later, the
  normal daily cadence, and the never-run case. The UTC round-trip tests remain.
- Version 3.10.129. No configuration or persisted-data migration; `last-run.json`
  keeps its format.

## Remaining risks

- **External, not code:** SYN's FTP host is unreachable, and `T:` needs SMB credentials.
  Both remain as described in v3.10.128.
- **Race queue backlog (capacity, not a defect):** a burst of 51 tv-hd season
  episodes arrived on `#supers` between 10:00 and 11:00. Queue waits reached **482 min**,
  and 18 queued races had not started by 19:01. Each race takes about 7 min, and
  superbnc → zephyr Relay runs at 6–9 MB/s. `maxConcurrentRaces: 1` and `loginHeadroom: 2`
  (4-login cap) are deliberate. A second concurrent race would split the same bandwidth.
  Changing queue policy, such as dropping stale releases or reordering by age, is an
  operator decision. This release does not change it.
- `ScheduleNext` can be entered concurrently from the `SystemEvents` thread and the
  run's `finally`. `_runGate` prevents overlapping runs. There is no evidence of an
  extra run from this path, so it was left unchanged.
- The first live check of the fix is the next 04:00 slot (2026-09-23).
- Rollback: the v3.10.128 installer. No data migration.
