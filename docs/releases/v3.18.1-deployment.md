# GL Drive v3.18.1: log audit, corrective release and deployment

**v3.18.1 was built, tested, published through the standard pipeline, installed on the production box and verified healthy during the post-deploy monitoring window.** Release commit: `f472892`. GitHub release `v3.18.1` (Latest) was published 2026-10-29 03:27:33 UTC with four assets: installer, update zip, `checksums.sha256` and its RSA signature.

## Audit scope

The audit covered all retained application logs for 2026-10-27 00:00 through 2026-10-28 20:00 local time (UTC−07:00): 21 files written by ten app versions (3.11.32 → 3.17.1). The Windows Application event log was checked for .NET Runtime 1026 and Application Error 1000 events.

- **ERR: 0 and FTL: 0** in every file. No GlDrive native crash events. The three `ReleaseCheck.exe` 1026 events on 2026-10-28 came from a developer harness run, not from the app.
- **WRN: 93 over two days.** By cause: SYN remount retries (external: the host has been down since 2026-08-13), PreDB fetch timeouts and 503s (external), superbnc RETR 550 / connection resets during source relocation (recovered by relocation-following), the 3.14.0 remount storm and the 3.15.1 source-hint failures.
- The 3.17.1 window was also checked by message, not just by level: 5xx/4xx replies grouped by command, INF failure-shaped lines with digits and release names normalised, and exceptions.

| 3 | v3.18.0 broke the native smoke harness (`tools/ReleaseCheck` did not compile) | `CertificateManager.TrustCertificate` became internal, `CertificatePrompt` was removed and `AttachTofuValidation` gained a parameter. `release.ps1` does not build the harness, so the break went unnoticed | **Fixed in 3.18.1.** `InternalsVisibleTo ReleaseCheck`, direct call instead of reflection |

## Deployment and production verification

- Pre-install snapshot: 3.17.1 (PID 54520), 1 race running and 47 queued.
- At 03:28:24 UTC the updater verified the `checksums.sha256` signature and handed off to the SYSTEM scheduled task (no UAC prompt). 3.18.1 was running at 03:28:51 UTC (PID 90636). The heartbeat reports `3.18.1.0`.
- **Race queue restored: 48 = 47 queued + 1 in flight, 0 dropped.** Racing resumed 12 s after start. The first race on 3.18.1 completed at 03:35:17 UTC with 22 FXP completes and no failed jobs.
- **Route memory written in production:** after the single expected first probe on this version (no file existed before), `fxp-relay-routes.json` holds `bb90928a→a8a08694 @ 03:29:27Z`, with no leftover `.tmp`.
- **Marker suppression observed live:** in the stored zephyr notifications, the releases at 03:22 and 03:28 UTC (3.17.1) each arrived as a pair: the release plus its `[incomplete]-` link. The first release on 3.18.1 (03:36:11 UTC, `LOL…Italy…S01E02`) produced a single entry.
- Post-deploy window (03:28:53 → 03:36+ UTC): **ERR 0, FTL 0, WRN 0.**

## Remaining risks and follow-ups

- **Persistence across a restart is shown by unit tests, not yet by a second production restart.** On the next restart within 6 h of 03:29 UTC there should be no `direct CPSV-PASV failed` line about 30 s after `GlDrive starting`. No restart was forced, to avoid another race interruption and BNC reconnect.
- **Stored notifications from before the upgrade still contain marker entries** (for example 127 zephyr items). The fix stops new ones; existing items age out normally and were not deleted.
- **The race in flight at install** (`LOL.Last.One.Laughing.Denmark.Halloween.Special.S02E03…`) was requeued for resume. It had not run again by the end of monitoring because the queue runs one race at a time.
- **`release.ps1` still does not build or run `tools/ReleaseCheck`.** The harness can break again without anyone noticing. Wiring it into the pipeline needs the Python fixture and an unlocked desktop for WinFsp, so this is left as a follow-up.
- **Open items outside the code (unchanged):** SYN's FTP host is still unreachable. `logging.level` is still Verbose (about 10 MB/hour; the 24-file cap keeps about one day of history). zephyr `-TV-` routing is still frozen pending Dave's decision.
- The superbnc→zephyr direct route has not succeeded since 2026-07-01. The 6 h re-probe (2 logins each) is now the steady-state cost, about 4 probes per day instead of one per restart plus every 6 h.
