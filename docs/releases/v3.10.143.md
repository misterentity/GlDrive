## Defect — the race queue lived only in memory while running hours deep

Evidence (10-02): **362 races queued, 191 started.** At `maxConcurrentRaces: 1` arrivals
outran throughput. The FIFO wait reached **6h22m** (Chumbak.2026.S01E16 was queued at 13:37
and started at 19:59), and reconstructing the queue from the log gave **156 races pending** at
20:00. The v3.10.142 deploy the previous evening dropped 9 queued races, which stayed lost.
The deploy runbook had been working around this by re-issuing races through `POST /races`.

Root cause: `SpreadManager._raceQueue` was an in-memory `Queue`. Every restart (deploy,
auto-update, reboot, crash) silently discarded it, and nothing logged the loss (recurring
pattern #2: the state behind a decision was not persisted; pattern #5: visible only as
volume). A second defect sat in the same path. `DequeueNextRace` dequeued blindly, then
`StartRaceInternal` threw "Need at least 2 connected spread pools" whenever a participant's
pool was briefly down. That race was logged once at WRN and lost.

Fix:
- `Spread/RaceQueueStore.cs` (new) persists queued **and in-flight** races to
  `%AppData%\GlDrive\race-queue.json` on every enqueue, start and finish.
- Restore at startup puts in-flight races first. It drops requests older than 24h, and it
  resumes an in-flight race at most twice, so a race that takes the process down cannot
  crash-loop. It also de-duplicates by release name.
- `DequeueNextRace` takes the first queued race that has at least two connected pools and
  leaves the rest queued. Every spread-pool registration drains the queue, so a restored queue
  starts as soon as the pools come up. Requests older than 24h expire there with a WRN.
- Dispose never writes, so shutdown, which stops every job, cannot erase the in-flight races
  it interrupts. Read-only (screenshot) managers neither restore nor write the file.

Not changed: the queue *latency* itself. That is a capacity limit (login cap →
`maxConcurrentRaces: 1`, Relay route between superbnc and zephyr). This release stops the
loss, not the wait.

## Remaining risks

- **Queue latency is unchanged.** At 1 concurrent race, a busy day still builds a multi-hour
  backlog, and late races still find their release relocated to `/recent` (the RETR-550 WRNs
  above). Raising throughput needs more logins on the source account or a working direct
  route (the 6-hourly CPSV-PASV re-probe still fails with `425`).
- The 24h expiry drops a release that waits longer than a day, and logs a WRN when it does.
- `PersistQueue`'s after-dispose guard has no automated test (it needs live jobs). It was
  verified by review and by the clean restart above.
- External items still open: SYN FTP host down, T:\ unmounted, D: short of space for the
  21.6 GB Dont.Be.Shy extraction, and the zephyr `-TV-` routing decision.
