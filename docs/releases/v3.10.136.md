# v3.10.136 — park watched archives on a full disk instead of burning retries

## Findings

Review covered the retained logs for September 23–25 (3.10.134 → 3.10.135).
**0 Error / 0 Fatal**; Warning volume 92 / 150 / 106 per day. After the
3.10.135 restart (10:18) there were 46 warnings, in four causes:

| Cause | Count | Owner |
| --- | --- | --- |
| Downloads parked: `T:\` not mounted | 26 | Environment (known) |
| SYN FTP host unreachable, remount backoff | 13 | Remote host (known, since 2026-08-13) |
| `Auto-extract failed` on `D:\x265\Dont.Be.Shy…-EDITH` + abandon | 7 | **Code + environment** |

The FXP `RETR 550` warnings from superbnc on September 24 were all releases that
the site had relocated from `/incoming` to `/recent`; the existing relocation handling
recovered them, and none occurred after 3.10.135.

### Root cause of the extractor failures

`D:` (8 TB) has **784 KB free**. It is both the `D:\x265` watch folder and the storage for
the local site. The 23 GB `Dont.Be.Shy.2026.HDR.2160p` set settled at 21:05 on September 24:

1. The first extraction ran for 7.5 minutes and used up **all remaining space** on the
   shared volume before it threw `There is not enough space on the disk`. Cleanup of the
   `.gldrive-tmp` file worked.
2. `ExtractFailureClassifier` has no rule for disk-full errors, so it treated the failure as
   Transient. That used up all five watch retries in about 10 minutes, then the extractor
   abandoned the set in `TransientAbandonLedger`.
3. That ledger is keyed on the volume-set fingerprint (part count + bytes). **Freeing disk
   space never changes that fingerprint.** The log said it would retry "after the folder
   changes", but that could not happen. Only a restart could revive the set, and each
   restart went through the same cycle again (the 10:17 and 10:18 restarts each did).

This is recurring pattern #3: the verdict was keyed on something other than the resource
that was actually short.

## Changes

- New `Downloads/ExtractSpaceParking` keys the verdict on the output **drive**.
- `AutoExtractItem` (the chokepoint all three routes pass through) now checks free space
  before extracting. The requirement is the volume-set bytes plus 1 GiB of headroom, so an
  extraction can no longer drive the shared volume to zero. Scene sets are stored (m0), so
  volume bytes ≈ unpacked size.
- A disk-full failure found mid-extraction (`ERROR_DISK_FULL` / `ERROR_HANDLE_DISK_FULL`
  via HResult, or UnRAR/Rar exit 5) now parks the set. It no longer calls
  `ScheduleWatchRetry`.
- Parking uses no retry and writes no abandon verdict. The existing 5-minute sweep checks
  again and re-offers the set as soon as its drive has room.
- No configuration or data migration.

## Remaining risks

- **D: is full (784 KB free).** This release stops GlDrive from writing into it. The set
  still needs about 22.6 GB free before it can extract, and it will then extract
  automatically within 5 minutes. The local site's uploads to `D:` are also at risk until
  space is freed. No user media was moved or deleted.
- **T:\ is still not mounted**, so 2 downloads are parked. **SYN's FTP host is still
  down.** Both are outside the code.
- The preflight uses volume bytes. A *compressed* archive can need more than that; if it
  does, the disk-full catch parks it instead.
- Paths parked for space live in memory. A restart re-checks them against the drive,
  which is correct, and logs one warning per set.
- The `#SYN-SPAM` catch-all announce rule noted on 2026-09-14 is still in the config
  (user setting, not changed).
- A 5-minute observation window does not prove multi-day stability.
- Rollback: the v3.10.135 installer restores the retry/abandon behavior. No data migration.
