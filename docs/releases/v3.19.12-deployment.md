## Changes and root causes

**1. Same-session Relay after a transport failure (.11).** When a direct source-CPSV probe threw anything other than `DirectFxpCompletionException`, the code fell back to Relay on the same two sessions. A FluentFTP read timeout leaves a command without its reply. Relay's first `TYPE I` then failed with `SelfConnectMode`, and the destination was backed off for a fault that wasn't its own. Same-session Relay now happens only after a clean reply rejection (`FaultSide` Source/Dest, set only by `Fault()`). Any other failure poisons both sessions and rethrows. Regression test: `DirectProbeTransportTimeoutNeverFallsBackToRelayOnTheSameSessions`.

**2. Direct FXP completion was capped by FluentFTP's ReadTimeout (.12, the real root cause of 1 and 3).** During a server-to-server transfer the control channel is silent until `226`. `ReadReplyManagedTimeout` enforced a managed deadline of `transferTimeoutSeconds` (60 in production). However, FluentFTP's `GetReplyInternal` re-reads `Config.ReadTimeout` (30 s, `FtpClientFactory`) on every call and throws first. So **every direct file slower than 30 s failed** and poisoned two logins. Evidence: failures at 18:16:35, 19:33:37, 19:43:10, 19:45:20, 19:46:05 and 20:01:38, each exactly 30 s after the file started. The completion read now widens the client's `ReadTimeout` to the deadline plus 5 s and restores it afterwards; on a managed timeout, it is restored once the draining read finishes on the poisoned connection. Regression test: `DirectCompletionWaitsForTheTransferCeilingNotTheReadTimeout`, a 226 arriving after the client's read timeout, for PasvPasv and the Relay-mode direct probe.

**3. One failure demoted a proven route for 6 h (.11).** siteb→sited ran direct 21/21 at a median of ~20 MB/s, about twice Relay's ~10 MB/s. Then the 18:16 timeout (cause #2) moved it to Relay for 6 h, and the verdict was persisted. A route that has completed a direct transfer this session now gets one failure of slack, and a second consecutive failure switches it. The slack is memory-only, so a route that has never worked direct still switches on its first failure, as in the July topology case. All three failure paths now log the consequence on the Information sink (two of them used to demote silently). On v3.19.11 this kept the route direct through four cause-#2 failures, each followed by successes.

**4. `550 … File exists` not recognized as a dupe (.11).** sited rejects a STOR that races another uploader's open with `550 System Error- <file>: File exists.`, alongside `553 File is being uploaded by …` for sibling files. `IsDupeRejection` accepted only 553. It now keys on the dupe wording for 550 or 553. Before, this cost a failed file and a poisoned source login on a 1-login source cap.

**5. The ioFTPD CPSV verdict was memory-only (.11).** Every restart re-learned sitea's "CPSV data peer stays TLS server" verdict by failing two listings. Each time that poisoned two sitea logins (a flood-ban-sensitive site), built a 0-entry index and logged `RefreshStatsAsync failed for sitea` (11:04 and 16:06 on 11-03). The verdict is now persisted in `%AppData%\GlDrive\cpsv-verdicts.json`, with expiry and renewal (renewals saved at most every 30 min per host). The test suite covers survival, expiry, persisted expiry, renewal and an unreadable file.

## Remaining risks

- **Fix #2 has not yet been exercised by a slow production file.** In the 15-minute window the slowest direct file took 18.2 s, so none crossed the old 30 s cap. The fix is proven by the regression test and mutation testing only. **Check:** the next day's `transfers-*.jsonl` should show `CpsvPasv` rows with `elapsedMs > 30000` and no abort reason.
- **Direct completions now have a 60 s ceiling** (`spread.transferTimeoutSeconds`), stricter than Relay's 1,200 s idle-progress deadline. A direct file slower than 60 s (about 150 MB below 2.5 MB/s) still fails, and repeated failures demote the route to Relay. That is a safe fallback, but if it shows up in logs the ceiling should scale with file size.
- **Direct-FXP preliminary wait:** the STOR/RETR 150 wait is still 30 s managed against 30 s native. A timeout there is now handled honestly (fix #1), but it could get the same widening as fix #2 if it is ever seen.
- **One manual state change:** before installing v3.19.11, I backed up and emptied `fxp-relay-routes-srccpsv.json`. It held the 6 h Relay verdict caused by bug #2, which would otherwise have stopped the fixes being exercised that night. The backup is in the session scratchpad; the file is `[]` now, so the route is direct.
- **External / standing:** SITEC FTP is still down (46 attempts since 10-28; Dave's site). Announce rules target unconfigured `#announce` and `#pre` channels on three servers. sited's `/TV-1080` is outside index coverage. The `-TV-` routing freezes still await Dave's decision. PreDB TLS provider outages can recur, and backoff handles them.
