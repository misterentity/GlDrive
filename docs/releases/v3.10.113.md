# GlDrive v3.10.113

Hotfix for a v3.10.111 regression that first ran in production as part of v3.10.112 (the box went 3.10.110 → 3.10.112 directly, so .111's code had never run live).

## Fix

- **Consuming a CPSV completion reply now clears the pending mark before the reply is validated.** v3.10.111 added `ValidateCompletion` inside `CompleteDataSequence` and placed it before `EndDataSequence`. A reply that has been read is no longer on the wire, so the channel is in sync whatever the code says; throwing first left the mark set and the pool discarded the connection. glftpd answers a fully relayed `STOR` with `426 Data Connection: Success.` (its data-close quirk) on every transfer, so the first race on v3.10.112 (2026-09-09 22:28, Big.Brother.US.S28E31) poisoned the destination after **12 of 12** successful relays and the source after **10 of 12** dupe-skip `ABOR`s, whose legitimate reply is also a 426. On the previous build those rates were 8 of 1,536 and 1 of 91. Exactly the v3.10.14 shape.
- `CompleteDataSequence` gained a `validate` flag (default strict). Receivers of a `RETR` keep strict validation, which is what .111 set out to add for media transfers. Senders of a `STOR` (`UploadFile`, `UploadFileStream`, the Relay destination) and the dupe-skip `ABOR` pass `validate: false`: their bytes were flushed before the reply. This restores the pre-.111 behaviour for those paths, where it had run for months.
- Side effect avoided: mounted-drive writes go through `UploadFile`; with strict validation every CPSV upload to a glftpd site would have reported a failure after a complete upload and left a `write-recovery` copy. Drive mounts are currently disabled on both live servers, so this had no symptom yet.

## Validation

- `dotnet test`: **1,258 passed** (8 new in `CpsvCompletionReplyTests`).
- Mutation check: five mutants (validate-before-clear, strict dest, strict ABOR, strict UploadFile, lenient path not clearing) — **5 / 5 caught**.
- Build 0 warnings.

## Production baseline to verify after deploy

- On v3.10.112 since 21:13 PT: 0 ERR, 0 FTL, 1 race (22 files) completed, 23 poisoned-discards, all adjacent to a successful relay or a dupe-skip, each accompanied by `Relay: N bytes delivered but completion reply failed (FTP transfer did not complete: 426 Data Connection: Success.)`.
- Expected after v3.10.113: that Information line disappears from successful relays, and poisoned-discards adjacent to `FXP complete` return to the sub-1% rate of 3.10.110.
