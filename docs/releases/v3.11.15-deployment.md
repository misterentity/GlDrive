## Investigation and changes

The original live torrent had metadata but no connected, available or connecting peers. All five tracker addresses were retained through metadata-to-payload handoff, ruling out tracker loss. Four of five independent scrape requests returned nonempty swarms; that does not guarantee peers will connect or offer wanted pieces. Read-only investigation and isolated reproductions identified four pinned MonoTorrent defects:

- Returned unsuccessful announce responses could be treated as completed operations by the tier scheduler, skipping a healthy fallback tracker. The adapter now converts those unsuccessful responses into the exception-based failure signal the scheduler expects.
- The underlying tracker did not retain its successful announce response, leaving retry intervals at constructor defaults. The adapter retains successful response intervals.
- UDP announces serialized enum ordinals for start/stop/completion instead of the standard wire values. The adapter now sends None=0, Completed=1, Started=2 and Stopped=3 while retaining the engine's semantic event and preserving HTTP/HTTPS behavior.
- The UDP parser stored the advertised ordinary interval as a minimum interval, leaving ordinary scheduling at the default 30 minutes. The adapter now uses the actual UDP response interval.

New tracker diagnostics contain scheme and status, not URLs, server messages or peer identities. In-flight transport requests remain owned until they settle; cancellation does not abandon a pinned UDP operation.

Queued torrents now inherit the engine's complete connection budget instead of the library's hidden default 60-peer per-torrent cap. The current engine budget is **100 total connections and 16 half-open attempts**, shared across active torrents. Queue rows distinguish waiting for peers from connecting to discovered candidates and show available candidate counts alongside connected seeds/peers.

New outgoing torrent peer sockets rotate across selected download networks, resolving current addresses at each connection. When multiple eligible routes exist, a failed route gives another selected route a chance after at most three seconds per attempt. Explicit IPv4 selections do not silently escape through an unbound IPv6 route. Received peer bytes, including protocol overhead, use the shared download pacer and per-network usage ledger. Allowance checks resolve the current saved settings, so replacing configuration objects affects an already-connected peer.

Standard PASV FTP data sockets now use the lane's selected source address, matching CPSV behavior. The temporary client bind setting is restored after success, setup failure or cancellation. Control sessions, shared login budgets, race priority and safe yield/drain rules remain authoritative; selecting two adapters does not create extra login permits.

## Remaining risks and limits

- More peer connections and two selected adapters do not guarantee 100 useful peers, additive WAN bandwidth or any particular speed. They remain bounded by OS routing, shared upstream capacity, remote upload limits, wanted-piece availability and engine limits.
- FTP is still limited by configured account caps and headroom: the observed configuration allows one main and one priority/race login per site. Race activity can correctly remove the borrowed lane. Both halves of an FTP split must satisfy the configured minimum; small remaining ranges need not use two lanes.
- The new per-network routing, pacing and usage ledger wrap outgoing torrent peer connections. Incoming peers retain the native listener/engine rate path, so this is not universal combined FTP/torrent accounting for every incoming connection. Tracker and DNS traffic are not bound by the peer factory.
- Existing connections are not migrated when adapter selection changes. Listener/DHT bindings are established at service construction. An explicit VPN preference takes precedence when available; missing adapters retain the existing warning/default-route policy, not a kill switch.
- The pinned UDP transport can delay cancellation until its in-flight request times out. The adapter drains it instead of returning while requests remain unowned. External tracker/bootstrap/swarm availability remains outside application control.
- The observed unavailable site, IRC access restrictions, bounded search-pool contention, individual UDP tracker failure and incomplete archive with **12 missing volumes** remain operational risks. Fresh warnings are classified above; this release does not claim all warnings were eliminated or all searches had complete coverage.
- Existing durable torrent safety tradeoffs remain: conservative full-size disk reservation on resume, startup/hash drains before writer ownership ends, existing skipped-file/crash limitations, and locally persisted magnets/metadata relying on Windows access controls rather than new encryption.
- This pipeline retained the existing Inno administrative-install/HKCU advisory at `release/release-pipeline.log:1464`. Alternate-admin standalone installer autostart ownership was not runtime-tested. Installer compilation succeeded; that advisory is not a failure of the separately verified signed-ZIP update path.
