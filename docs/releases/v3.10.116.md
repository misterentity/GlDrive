## Findings and fixes

**Poisoned discards were unattributed.** The pool's quarantine line is the only record of a spent login, and it read `poisoned-discard` for all 28 poison sites alike. In the window with named pool lines (v3.10.114 onward) superbnc had 20 discards and zephyr 9. Most sit next to a line naming their cause (a rejected STOR, a transport reset, the 6-hourly direct-route re-probe). Six superbnc discards had no such line. One at 18:24:55 on September 11 followed 18 s of something holding the single main-pool connection before a scan's borrow timed out; nothing in the log says what held it.

- `PooledConnection.Poison(reason)` records why a connection was poisoned. The first reason wins, so the site nearest the failure names it and the generic attribution later in the finally chain does not overwrite it. All 28 production sites now pass a reason.
- The pool prints it: `Pool[superbnc]: quarantined connection (poisoned-discard: scan LIST /x: data-channel deadline, ...)`. A connection discarded only because a CPSV data sequence left a reply outstanding says so. A bare `Poisoned = true` prints `unattributed`, and a structural test rejects any new one in production code.

**A deadline inside a scan LIST was reported as pool exhaustion.** The 10 s data TCP connect and 10 s data TLS deadlines in `CpsvDataHelper` surface as the same `OperationCanceledException` as the scan's 20 s borrow timeout. `ScanDirectoryRecursive` poisoned the connection and rethrew; the caller then logged `main pool exhausted, falling back` and `ScanFailureClassifier` read it as contention. The classifier's own comment states the premise it violated: "a borrow that timed out or was cancelled never opened a connection." This one spent one. Found from the code while tracing the 18:24:55 discard, not from a confirmed occurrence in the retained logs.

- A cancellation that is not the caller's token is wrapped as `ScanListingFailedException`, as is an unclean `IOException`. The caller's own cancellation still propagates as a cancellation.
- The scan's main-pool branch logs the listing failure with its cause before falling back. The previously silent catch-all now logs too.
- The classifier treats the new exception as a fault, including when a caller wraps it.

**A failed `ABOR` after a Relay dupe-skip was invisible.** In Relay mode the source `RETR` is accepted before the destination rejects the `STOR` as a dupe. The code then sends `ABOR` to bring the source back in sync and reuses it; if that throws, the source login is spent. Of 248 Relay dupe-skips on September 10 and 11, 3 poisoned the source, and the only log of the cause was `Log.Debug` on an Information sink. It now logs at Information with the exception type and message.

## Remaining external failures and risks

- SYN's FTP host is still unreachable (81 remount attempts in three days, each at the Windows 21 s SYN-retransmit ceiling). Its IRC host answers. Only the server or network owner can fix this.
- superbnc stalled for five minutes twice on September 10 (08:38 to 08:43 and 23:50 to 23:51): dial timeouts every 30 s, the GnuTLS drain warning, and 13 borrow timeouts naming the main pool as the permit holder. The permit holder was a dial that had not yet failed. This is the server-side stall already on record; the borrow-timeout diagnosis was correct.
- zephyr keeps answering `425 Can't build data connection: Connection refused` to a small share of STOR, RETR, and LIST commands. The destination backoff ladder absorbs it. A server-side cause cannot be proven from this side.
- The two watchdog restarts without a clean-exit marker on September 11 (09:23 and 09:28) fall inside the seven minutes between the v3.10.115 release being published and the updater applying it, with no crash event in the Windows event log. They match the operator-restart pattern recorded for earlier updates. None occurred on v3.10.115 through 19:00.
- Memory: the heartbeat showed 301 MB working set after about 9.5 h on v3.10.115. That is one sample, not a trend; the v3.10.106 leak reached 911 MB at 51 h, so the next sweep should compare against uptime.
- This release changes log text and exception typing on the scan path, not transfer behaviour. The risk is a caller that catches `OperationCanceledException` or `IOException` from `ScanDirectoryRecursive` and now sees the wrapper; the only caller is the scan's own dispatch, which was updated. Roll back with the v3.10.115 installer if a regression is confirmed.
