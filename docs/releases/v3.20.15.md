## Recover spread participants safely

A server that was unavailable when a spread job was created could later recover
and rejoin its pool registry without a corresponding progress record. Scheduling
a transfer then failed with a missing dictionary key, aborting the race. The
November 9 log review found 135 such failures in the retained production logs.

- Initialize per-site progress before publishing recovered connection pools.
- Preserve existing transfer counters when pools are replaced, and retain source
  roles when failover discovers another source.
- Keep progress enumeration safe while recovery adds sites, preventing a concurrent
  collection-modified exception in UI or completion readers.
- Preserve exception context for unexpected race failures to make future diagnosis
  actionable.

Regression tests exercise recovered participants through transfer scheduling and
slot accounting. The release is validated with the full automated suites, native
FTPS/WinFsp and CPSV/login-sharing fixtures, and UI smoke checks.

Remote directory-creation restrictions, missing remote content, idle disconnects
and account login limits remain external operating constraints. This fix does not
change server permissions, user routing, credentials, or connection safety limits.
All 5,889 automated tests and native/UI smoke checks passed. The installed app
passed 15 production health samples, while the strict operation monitor recorded
one recurring remote directory-permission failure. See the
[deployment report](https://github.com/misterentity/GlDrive/blob/master/docs/releases/v3.20.15-deployment.md)
for release integrity, installation evidence and remaining limitations.
