# v3.11.14 — Player torrents in the main Downloads queue

The player's Download action queues torrent content in the same persistent
Downloads interface as FTP content. Each torrent has its own destination folder
and continues independently of the player window or playback session. The
industrial terminal presentation remains in place, with BitTorrent source labels,
metadata/peer status and progress in the main queue.

## Queue and transfer behavior

The shared download manager owns scheduling, progress persistence, pause/resume,
cancel/retry, disk reservations and optional extraction. A dedicated MonoTorrent
engine owns peer transfers and piece verification. FTP connection sharing and its
separate main/spread pools retain the v3.11.13 fixes.

Metadata and file-policy checks run before payload writes. Unsafe destination
paths cannot be overridden. A mixed torrent containing blocked extensions needs
explicit approval to skip those files; no permitted files means no download.
Completion requires verified selected pieces and closed writers before extraction
or a Completed status. Private tracker-bearing magnet links remain in the
restricted local queue file and are omitted from automation responses and download
telemetry.

Pause survives application restart. Immediate resume/retry waits for the previous
writer to close, including when cancelled history is removed. Paused archives
remain protected from watch-folder extraction. Cached metadata is screened again
on resume, and backend cleanup preserves fast-resume data.

The old player-owned download list was transient and shared the player's lifetime.
The new application-owned queue removes that dependency. Tests also exposed
MonoTorrent's default cache deletion on removal, its asynchronous startup racing
Stop/Remove, and an owner/session disposal lock inversion. Cleanup now preserves
cache data, waits for startup to settle and runs outside those locks.

## Operational limits

- FTP and torrent transfers share queue behavior and disk reservations. FTP's
  byte pacer and MonoTorrent's rate cap remain separate bandwidth budgets.
- Torrent disk admission conservatively reserves the full selected payload,
  even on resume, because persisted byte counts cannot prove existing files are
  still valid. A nearly full destination may need additional free space.
- Peer availability controls download speed and metadata discovery. Local tests
  do not establish availability or throughput of a public or private swarm.
- A shutdown that exceeds the bounded drain may require piece rechecking on
  restart. Existing MonoTorrent VPN-binding and skipped-file shared-piece/crash
  limitations still apply; this integration does not change the pinned engine.
