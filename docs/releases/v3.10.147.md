# v3.10.147 — validate every Relay completion and preserve cancellation

## Log review and root causes

Reviewed the retained application logs, transfer/race telemetry, Windows Application
events, installed process, heartbeat, control API, and external dependency reachability
on October 6, 2026. The running baseline was v3.10.146, PID 46844, started at
03:21:53 UTC. Local log timestamps are UTC−07:00.

The audit captured at 17:06:40 UTC covered 19,783 retained log records (October 4–6),
including 308 warnings and no Error or Fatal records. Since v3.10.146 started there
were 4,086 records and 57 warnings; Windows Application events had no GlDrive
Error/Critical entries. All 81 recorded race outcomes were complete. Of 1,410 transfer records, one
failed after a remote reset; the same file completed on retry 7 minutes 36 seconds
later, followed by race completion. Direct CPSV/PASV probe failures used the existing
Relay fallback and six-hour route cache. One AI-provider HTTP 429 recovered on retry
at 11:02:38 UTC. Every one of the 12 earlier aborted race outcomes had a later complete
outcome, including work restored after the previous updater restart.

The review also revisited the truncated Relay root cause from v3.10.146. That release
checked the known file size only when completion-reply reading threw an exception.
Two concrete gaps remained:

1. Successful FTP completion replies bypassed the size check, so a short source EOF
   could still mark the file complete and receive ownership/delivery credit.
2. The full-byte exception filter also caught cancellation during reply reading,
   converting a cancelled operation into a successful transfer.

These two paths were reproduced with behavioral tests. Neither was observed as a
new occurrence in the current-process telemetry; they are corrections to the
previous incident's incomplete completion policy. Expected file sizes are not saved
in historical transfer telemetry, so absence of isolated short successes cannot be
proven retrospectively.

## Changes

- Apply the known-size check after successful completion replies as well as failed
  replies. A short file throws and follows the existing retry/quarantine path.
- Preserve cancellation before/during/after completion reply handling. A full byte
  count does not override caller cancellation.
- Keep measured Relay bytes available when completion fails.
- Preserve accepted behavior for full/growing files, valid empty files with successful
  replies, unknown sizes, and the destination's existing glftpd completion-reply quirk.

## Remaining risks

- **External storage:** T: is absent, so downloads remain parked. The configured x265
  category also points to absent M: (a dormant configuration risk). No SMB drive mappings
  were present. Restoring the intended drives requires the storage target/mount details;
  silently redirecting downloads would change where user data is stored.
- **External FTP:** SYN's configured endpoint still timed out in a bounded TCP probe.
  The other two baseline FTP servers were connected. The application retains capped
  reconnect attempts; it cannot restore the remote host/network.
- **External PreDB:** HTTPS requests began timing out during this review. An independent
  HTTPS probe also timed out during the TLS handshake. Existing retry backoff applies.
- A Relay with an unknown source size cannot prove completeness from byte count;
  existing completion/re-scan behavior remains. The loopback native smoke harness
  does not emulate every remote glftpd/BNC condition.
- Race queue latency remains constrained by the configured single concurrent race
  and remote login capacity.
- Two older torrent metadata deadlines have no verified recovery; the selected peer
  swarms did not provide metadata before the bounded deadline.
