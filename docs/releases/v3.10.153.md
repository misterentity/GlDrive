# v3.10.153 — follow a mid-race source relocation immediately

## Log review and root cause

Reviewed the retained October 7–9 application logs (local UTC−07:00), Windows
`.NET Runtime` 1026 events, the watchdog record and the installed v3.10.152
process (PID 89632, started October 9 10:22:44 local). Since that start there were
**zero Error/Fatal records** and no production crashes. All five 1026 events in the
window were release-verification tooling (`ReleaseCheck.exe` deliberate red runs and
harness builds), not GL Drive. Four watchdog-mediated updates completed cleanly.

Warnings since the v3.10.152 start were external or self-recovering:
absent T: drive parks (26), SYN FTP host unreachable (13), and 16 lines from
seven source files that 550'd while superbnc moved two releases from
`/incoming/tv-hd` to `/recent/tv-hd` mid-race. Both races, and the four similar
races on October 7–8, completed with zero files undelivered.

The relocations still cost time. In every case the race kept issuing RETRs at
vanished files for 17–25 seconds before following the release:

- **Probe order.** `RelocationCandidatePaths` listed every configured section
  dir before the notification watch path. superbnc has 15 sections, so
  `/recent/tv-hd` (where the move always lands) was the 15th sequential
  `DirectoryExists` probe, each on a newly borrowed connection. The first 550 to
  "relocated" took 17–19 seconds in 5 of 6 cases.
- **Mid-move misjudged as transient.** A cross-filesystem move deletes files
  before the directory. On October 9 10:38 the confirming probe found the old
  dir still listed and returned "transient, not migrating" without checking the
  relocation candidates. Five more transfers failed and every file was marked
  failed (`failures=20`) until the next scan saw an empty listing 25 seconds later.

Fix (`Spread/SpreadJob.cs`):

- Relocation candidates under the watch path are probed first. Section order is
  kept within each group. The Phase-1 source probe (`CandidateBasePaths`) is unchanged.
- `FindRelocatedSourcePath` reuses one borrowed connection across candidates. A
  probe that throws poisons it, and the next candidate borrows a fresh one.
- `HandleSourceMigration` always runs the relocation probe. "Transient" is
  reported only when the old dir is present and no relocation target exists.
  When the old dir still lists but the release already exists at a candidate,
  the race follows it now. The log line says "(mid-move: old dir still listed)".

Not changed: the AgentRunner logs "next run in" 2–3× together on Windows
`TimeChanged`/resume events (daily ~03:42 w32time sync). Every day still had exactly
one scheduled run (plus one legitimate HTTP 429 retry on October 9), and
`_runGate` prevents overlapping runs. One search-index LIST hit machine-wide
port pressure ("Only one usage of each socket address") at 16:42. The v3.10.149
guard handled it and the index kept growing.

## Remaining risks

- The relocation path is exercised by unit/structural tests only. The native
  smoke has no mid-race move, so live proof means waiting for the next superbnc
  `/incoming` → `/recent` move. Tell: "relocated the release" within ~1–3 seconds of
  the first `RETR failed: 550`, or the "(mid-move: old dir still listed)" suffix.
- On a site whose `/recent` mirrors `/incoming` (symlinks), a transient 550 now
  re-points the source at the mirror path. Same content, so harmless, but the
  source path in logs may switch to `/recent`.
- Operator items unchanged: T: not mounted (two parked downloads), SYN FTP host
  down, D: space.
