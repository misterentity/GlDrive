# v3.10.149 — distinguish Relay duration expiry from inactivity; resilient search index

## Follow-up log review (2026-10-08 03:00 UTC)

Re-reviewed everything logged after the 2026-10-07 17:08 UTC audit (v3.10.148, PID 26988):
**zero Error/Fatal**. Warnings were the known external conditions (T: unmounted → 2 parked
downloads, SYN FTP unreachable → remount attempts), two RETR 550s on releases the source
moved to `/recent` (followed and completed), one remote connection reset on superbnc→zephyr
(retried), and one new incident:

- **16:12 local: search-index crawl hit WSAEADDRINUSE (10048) on 1151 zephyr listings.**
  The machine had run out of ephemeral ports: a live check found 5,439 TIME_WAIT sockets,
  5,244 of them loopback in adjacent (N, N+1) port pairs — socketpair churn from another
  local process, not GlDrive (GlDrive held 20 sockets). It drained to ~800 within minutes.
  GlDrive amplified it: the crawl kept borrowing for every listing, pool re-logins hit
  zephyr's 6-login cap (`530 restricted to 6 simultaneous logins`), the pool entered a 90s
  BNC cooldown, NewReleaseMonitor missed a poll and ConnectionMonitor dropped/reconnected
  (recovered in 22s). The published index then lost ~1100 entries (5,514 vs ~6,600) for an hour.

**Fix:** `FtpSearchService` crawl aborts after 5 consecutive listing failures and keeps the
previous index whole; sporadic failures carry the previous index's entries under each failed
directory forward instead of dropping them. 7 new tests in `SearchIndexCrawlTests`.

## Fix

Source review of the previous timeout fix exposed a separate **diagnostic defect**,
not a newly observed production timeout. Relay progress re-arms the outer
inactivity deadline (180 seconds at the current setting), allowing a slow transfer
to reach its independent total-duration deadline (1,200 seconds). Both previously
surfaced as `OperationCanceledException`, and the caller labelled every Relay
cancellation `no progress for 180s`, even if bytes were still flowing.

- Tag cancellation at the Relay loop only when its own duration timer expired and
  the caller's token was not cancelled. Preserve the original exception/token.
- Report `relay duration ceiling 1200s` for that proven cause. Share the duration
  calculation between enforcement and diagnostics so the reported value agrees.
- Preserve outer inactivity/wall-clock labels. Unidentified transport cancellation
  is reported as cancellation with an unattributed cause, without inventing a timer.
- Keep existing timeout values, progress callbacks, byte accounting, parent/job
  cancellation, retry accounting and connection quarantine behavior.

## Remaining risks

- Machine-wide ephemeral-port exhaustion from a non-GlDrive process can recur. GlDrive now
  degrades gracefully (stale-but-complete index, no login storm), but pool/FXP connects can
  still fail during such a burst. The churning process was not identified (it had stopped
  before sampling caught it).

- T: and M: must be restored by the storage/network owner; SYN's configured FTP
  endpoint remains unreachable. This release does not restore these dependencies.
- No successful live transfer exceeded 180 seconds in the baseline window, and no
  live Relay duration expiry occurred. Deadline attribution is exercised with real
  cancellation tokens in deterministic tests; a live long-relay soak is still pending.
- Remote source moves, resets, API timeouts and rate limits can recur. Recovery
  observed in this window is not a guarantee of future upstream availability.
- The native fixture verifies loopback FTPS/GnuTLS/WinFsp behavior, not every remote
  glftpd/BNC topology. Production observation is bounded and cannot establish
  long-term reliability or verify all remote file contents.
