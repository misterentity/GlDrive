# v3.11.10 — races release their logins when they finish; crash dumps keep their log

Found in the 2026-10-10..14 log sweep (v3.11.8 running at 0 ERR / 0 FTL).

## Fixes

- **A finished race no longer keeps scanning.** When a race completed, its
  background directory scan (and SFV read) kept running on a token that was
  disposed but never cancelled. It went on borrowing the account's logins for up
  to ~55 s, competing with the next race. On 2026-10-14 at 11:51:29 one of these
  scans poisoned a superbnc login 28 s after its race had completed. Ending a race
  now refuses new borrows and waits for any LIST already in flight, which is never
  torn mid-stream, before cleanup and history run.
- **Honest scan-failure warning.** "Spread scan FAILED ... (both pools
  unavailable)" was printed even when a connection *was* borrowed and its LIST
  data channel timed out. The cause now comes from the exception: "listing failed
  after borrow: ...".
- **Crash dumps include the log tail again.** 26 of 30 crash dumps on the
  production box said "failed to read today's log: ... being used by another
  process". The tail is now read in shared mode from the live file, following
  `_001`/`_002` size rolls.
- **Watchdog lines go to the live log.** After a size roll, watchdog and
  pre-startup lines went to the stale base file, out of time order. On
  2026-10-13, relaunch lines from 20:32–22:06 were missing from `_002`. The
  watchdog also never moved past the day it started. Both now resolve the live
  file on every write.

## Validation

- Release build succeeded with 0 warnings and 0 errors. All 2,192 unit tests pass
  (25 new).
- All 12 mutants of the new guards were killed. One guard that a mutant showed
  was not load-bearing was simplified.
- Smoke test: a second instance launched against the running v3.11.8 wrote its
  audit line into the live log while Serilog held it open.
