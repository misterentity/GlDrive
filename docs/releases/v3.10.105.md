# GlDrive v3.10.105 release record

## Findings and root causes

Retained application logs for September 2–4 (168k lines) contained no `ERR` or `FTL` records.
The sweep therefore trended warning volume and the exception census instead.

- **Ghost-kill storm (fixed).** 2026-09-04 03:02:31–03:02:51: seven "Pool: ghost kill (once per
  episode)" lines in 20 seconds against one account, four "Pool exhausted" borrow failures, and
  one FXP file (`r03`) failing four times in a row. The per-pool episode flag re-arms on every
  successful connect, and a `!user` login frees a slot so the next connect always succeeds; the
  "once" guard was inert under sustained pressure. Each kill also terminates the account's live
  sessions, which failed the in-flight transfer, which poisoned a connection into its 20 s
  deferred-teardown quarantine, which tripped the login cap again. The pool's own header comment
  records that six kills in four minutes tripped a multi-minute BNC cooldown on 2026-05-20. The
  trigger was benign: glftpd relocated the release from `/incoming` to `/recent` mid-race, so
  RETR returned 550 for a few files until the v3.10.101 relocation handler followed it.
- **Race-history load failure (no code defect).** One `JsonException` at 09:33:55 on September 3:
  `$[1].StartedAt` held `09/03/2026 14:50:37`, an invariant-culture format the application never
  writes. The v3.10.101 release record documents a manual data-recovery reconstruction that
  morning; the automatic `.corrupt` snapshot is that rejected first reconstruction (499 of 500
  rows in the foreign format). The store correctly refused to save over it, and the next
  successful load cleared the guard. The live file parses cleanly (500 rows, all ISO-8601).
- **Watchdog "exited without a clean-exit marker" ×5 (operator-caused).** Every occurrence sits
  30–60 seconds before an auto-update pick-up at the release times on September 3 and 4 and was
  followed by the new process finding the update; these were external kills during release
  smoke-testing. The two "Second GlDrive instance blocked" warnings are the v3.10.102 guard
  working as designed against the same launches.
- **External, unchanged.** SYN's FTP host is still unreachable (96 remount warnings, retried every
  5 minutes). Twelve `NewReleaseMonitor` polls in three days failed with `LIST 425 Can't build data
  connection`, each a single miss recovered on the next 60 s cycle. PreDB timeouts backed off as
  designed. Two `530 The site is full` logins on superbnc.

## Changes

- New `GhostKillThrottle` (`Ftp/GhostKillThrottle.cs`): per-account minimum interval between
  `!user` logins, default 60 s, longer than the 20 s deferred-teardown window that sustains a
  false login-limit reading. A refused attempt does not move the clock.
- `FtpClientFactory.KillGhosts` consults the throttle before creating a client and now returns
  whether a kill was issued. One factory serves every pool for a server, so the limit is
  account-wide, not per pool.
- `FtpConnectionPool` counts and logs a ghost kill only when one was issued, and skips the
  post-kill retry connect when the kill was suppressed.

## Validation

- New `GhostKillThrottleTests`: 8 tests, including the observed production cadence (7 attempts in
  20 s yields exactly 1 kill), a 32-thread race for a single permit, and two factory wiring tests
  that exercise `KillGhosts` for real against a refusing loopback port in both directions.
- Two mutants verified caught, with the file diffed after each mutation and restored after:
  factory ignoring the throttle (1 test fails) and a refusal advancing the clock (3 tests fail).
- Full suite: 1,142 passed, 0 failed, 0 skipped. `dotnet build` of `GlDrive.csproj` succeeded.

## Remaining risks

- The 60 s interval is a judgment: a genuine ghost that appears within 60 s of a kill waits up to
  a minute for the next kill. The prior behaviour would have severed live transfers instead.
- `loginHeadroom: 2` still caps FXP at one concurrent transfer per site (configuration, not code).
- SYN's FTP endpoint remains down; no code change can move that.
