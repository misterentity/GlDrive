## Defect found below warning level

Across 854 completions, the INF log showed **55 `FXP dupe-skip` events for files this client had uploaded itself 11–44 s earlier** ("It was uploaded by entity (0m 18s ago)"). A dupe-skip ties up a transfer slot and both logins for a Relay RETR/STOR round trip, and it delivers nothing.

Timeline for one example, `the.split.up.s01e02…r65` (14:07):

| Time | Event |
| --- | --- |
| :06.338 | zephyr `LIST` returns 8 files (r65 not yet there) |
| :09.772 | `FXP complete: …r65` — ownership recorded for zephyr |
| :11.288 | The :06 listing is **applied** (it waited on the slower source listing in the same batch) |
| :42.357 | r65 re-sent → `FXP dupe-skip (Relay)` |

**Root cause.** A scan listing is a snapshot from when `LIST` ran, but `SpreadJob.ProcessFiles` applies it later, after the whole scan batch finishes. `FileOwnershipReconciler.Prune` (v3.10.107) treats "owned before, absent now" as a deletion. Any completion recorded between the snapshot and its application was therefore revoked. The file was re-selected and marked in-flight at once. `Observe` skips in-flight files, so the 5–13 correct listings that followed could not restore ownership before the pointless re-send ended in a dupe-skip. A snapshot taken mid-upload can cause the same revocation through `Observe`'s size check, because it shows a partial size.

**Evidence.** A script over the log found the ordering `LIST returned < FXP complete < listing applied` for **55 of 55** dupe-skips. Overall, 168 zephyr completions landed in that window. The rest were re-observed before being re-selected.

## Fix

- `SpreadJob` keeps a monotonic ownership epoch under `_ownershipLock`. Each confirmed transfer stamps `(file, dest)` with a new epoch. Each scan task captures the current epoch **before** its `LIST` runs.
- `ProcessFiles` treats a file whose ownership on that site was confirmed after the listing's epoch as in-flight for `Observe`. That listing's size cannot demote it. The same predicate goes to `Prune`, so the file's absence from that listing does not revoke it.
- Later listings (captured after the stamp) apply normally. A genuine deletion is still pruned on the next cycle, which preserves the v3.10.107 phantom-volume behavior.
