# GL Drive v3.19.3: log review, corrective release and deployment

**v3.19.3 was built, tested, published through the standard pipeline and installed through the signed updater. All 5,463 regression tests passed, all 1,339 installed files match the release, and all 56 saved requests were retained. A 10.52-minute production watch found a stable local runtime with zero errors, fatal events or crashes. FTP availability remains degraded: Zephyr and SYN remain disconnected under recorded outage backoff, so cross-site racing is not currently operational.**

## Audit scope and findings

The retained-log inventory contained 1,380,248 records from October 28 through October 30. Prior versions had already been reviewed for v3.19.1 and v3.19.2. This release's fresh audit covers the v3.19.2 process from **2026-10-30 03:41:10 UTC to 17:01:51 UTC**: **24,987 records, 13,227 warnings, zero errors and zero fatal records**. Information-level failure messages and Windows Application crash events were also inspected. Zero ERR/FTL did not mean normal operation.

| Finding | Evidence and root cause | Correction |
|---|---|---|
| Scans amplify a remote outage | 7,576 individual scan warnings and 5,582 all-scans-failed summaries. Typed `FtpLoginHeldException` meant the local guard denied a new login before network I/O; the scanner treated it as a hard failure, tried the same held account's other empty pool, and repeated every few seconds. | Remember the deadline per site and pool pair; skip unavailable held pools and suppress repeated fallback/batch noise. Idle authenticated sessions remain usable. A real LIST failure after borrow remains a warning even if fallback meets a hold. Missing/stale deadlines receive a finite 30-second retry. |
| Races and pool recovery keep trying held endpoints | 38 reinitialization warnings, 194 completion sweeps and 1,399 no-candidate diagnostics. Registered empty pools counted as available; scans never told the active-race waiting path about admission holds. | Return blocked races to the durable queue. Pool/factory holds govern initialization, reinitialization and queue eligibility; an existing timer wakes due work. Preserve the only known source instead of starting against unrelated peers. Confirmed account recovery and a merged usable source wake the queue. Pool replacement cleans up failed candidates and rejects stale publication. |
| Zephyr FTP becomes unreachable | Existing connection failed with `GNUTLS_E_PULL_ERROR` at **05:35:47 UTC**, followed by timed-out reconnects. 13 reconnect warnings and 12 bounded hourly index-abort warnings; index retains its previous 3,236 entries. | The scheduling defects are corrected. Remote endpoint availability remains outside this code fix; logs establish connection loss/timeouts, not the remote system's internal cause. |
| SYN FTP remains unavailable | Four mount/remount warnings; ordinary retries respect the four-hour health backoff. | Preserve health evidence and configured retry policy. |

All 13,227 fresh warnings are accounted for: 13,158 scan summaries/individual failures, 38 reinitialization failures, 13 monitor reconnect failures, 12 search-index aborts, four SYN mount/remount failures, one release-monitor connection loss and one connection-monitor loss. No GlDrive crash event was found after the v3.19.2 deployment. Fourteen clean races and 180 completed FXP transfers preceded the Zephyr outage; healthy-site downloads continued afterward.

## Remaining operational risks

- Zephyr and SYN were unavailable during the audit. A healthy local process and corrected retry scheduling do not establish recovery of those remote FTP services.
- An extended live BNC/FXP soak and end-to-end transfers to unavailable endpoints cannot be completed until they recover. Native disposable fixtures exercise FTPS, CPSV sharing and WinFsp independently of production credentials.
- **No live cross-site race or endpoint recovery was observed after installation.** Restart left the unavailable pools absent, so the production watch does not directly exercise the original registered-but-exhausted scan/reinitialization path. The red-to-green regression tests establish that correction and its recovery behavior; the watch establishes stable operation under the continuing outage.
- The unchanged auto-race admission policy **skips new announces when fewer than two spread pools are connected**. These produce one warning per skipped announce, distinct from the fixed scan retry flood. This guard runs before section/rule filters, so the warnings do not establish that each announce would have been eligible to race. The 56 previously queued requests are retained, but fresh outage-period announcements are not automatically replayed. Ordinary queue age/resume limits also remain in force during a prolonged outage.
- Existing configuration notices remain: six example announce rules refer to unconfigured `#announce`/`#pre` channels; Zephyr `/TV-1080` index coverage and frozen section-mapping proposals require the owner's configuration decision. No intentional freeze or endpoint setting was changed to hide these notices.
- The persisted direct-FXP relay-route policy and signed updater's rollback probation are retained. Production rollback was not deliberately triggered.
- Inno Setup emitted its existing warning that the admin installer writes a per-user HKCU autostart entry. The .NET builds were warning-free and packaging succeeded. Installation using a different administrator account can target that account's user area; that fresh-installer scenario was not exercised. This deployment used the signed ZIP updater, which does not run the installer's autostart registry task.
