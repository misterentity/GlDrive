# v3.10.131 — the crash watchdog no longer dies with its launcher

## Log review and root causes

Reviewed the September 21–23 logs on September 23, 2026 (America/Vancouver).
There are **0 Error/0 Fatal** events. The finding that mattered was not in the
error stream: **GL Drive was not running at all.** The log stops mid-stream at
10:26:04, the last heartbeat is 10:27:31 (v3.10.130, PID 35276), the `.running`
marker was left behind, no watchdog restart line exists, and there is no
Application/System crash event. The app was down for about 9.5 hours, until
20:02.

- **Outage root cause:** the v3.10.130 deployment session (a Codex agent) used
  Restart Manager `RmRestart` from inside its sandboxed shell. RmRestart relaunches
  the app as a descendant of the caller, so the relaunched GL Drive, **its
  watchdog**, and the watchdog's post-update relaunch (PID 35276) all inherited
  the shell's job object. The session's last event is 10:27:39, and the app died
  between the 10:27:31 heartbeat and the next one. Terminating the job killed the app
  and watchdog together, so nothing was left to observe the exit or restart it.
- **Code defect:** `SpawnWatchdog` used a plain `Process.Start`, so the watchdog
  always shares its target's job. A watchdog that dies with its target cannot do
  its job. Normal logon autostart (explorer, no job) never hits this, but any
  launch from a job, such as an agent shell, a tool runner or a scheduled task, does.
- **Known external warnings, unchanged:** SYN FTP host TCP timeouts (the host has
  been down since 2026-08-13); `T:` not mapped, so two downloads remain parked without
  consuming retries; and transient FXP source relocations/resets that recovered.
  The v3.10.130 notes already analysed these, and no code change applies.

## Changes

- New `Services/JobBreakaway`: detects whether the process is in a job and the
  job's breakaway limits. It launches with `CREATE_BREAKAWAY_FROM_JOB` via
  `CreateProcessW`.
- `SpawnWatchdog` spawns the watchdog outside the job when the job allows
  breakaway, or when the job state can't be read. Otherwise it falls back to the
  old launch.
- Startup logs `Watchdog: launched inside a job object; watchdog spawned outside
  it…` (INF). It logs a **WRN** when the watchdog could not break away, because
  in that case a job termination leaves no other evidence.
- Version 3.10.131. No config or data migration.

## Remaining risks

- **A job that forbids breakaway** still takes the watchdog down with the app.
  The startup WRN now names this case explicitly. Launching GL Drive from the
  desktop or at logon is unaffected.
- **Operator rule for agents:** never restart production with `RmRestart`, a
  plain `Start-Process`, or `explorer.exe <path>` from an agent shell. All three
  land the app in the agent's job; `explorer.exe <path>` spawns a new explorer
  inside the job. v3.10.131 protects the watchdog, and the watchdog then relaunches
  the app outside the job, but only after the agent session kills the first instance.
- SYN is down and `T:` is unmapped. Both are external and need operator action.
- The observation window was short (about 7 minutes); no race ran during it.
- Rollback: the v3.10.130 installer. No data migration.
