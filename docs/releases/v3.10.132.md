# v3.10.132 — complete races that already reached their sole receiver

## Log review and root causes

Reviewed retained September 22–24 logs on September 24, 2026 (America/Vancouver).
Snapshots contain 46,359, 1,834 and 6,795 events respectively, ending at
10:02:05 PT on September 24. There are **0 Error and 0 Fatal** events; warnings
and recovery messages were also reviewed. Initial directory metadata misleadingly
showed today's log ending at midnight; reading a snapshot confirmed current
logging and transfers. No new logging defect was found.

- **Incorrect race failure:** two September 23 announces originated on zephyr,
  the sole receiving site. Discovery found the release there; the other peer,
  superbnc, lacked it and was download-only. The early two-site minimum check
  reported `Need 2+ servers` before the existing already-present no-op handling.
  This produced false configuration failures in logs, history and telemetry.
- **SYN:** mount/remount timeouts remain an external outage. A fresh five-second
  TCP probe timed out. Both other FTP servers remain connected.
- **T: downloads:** the destination drive is still absent. Two downloads remain
  parked without spending retry budgets. Restoring the intended drive/share
  requires operator credentials or infrastructure repair; no destination was changed.
- **September 24 transfer warnings:** two RETR 550 failures followed a source
  release relocation; the engine followed the new path and completed that race.
  Two remote connection resets recovered through retry. Each transfer warning
  also has a job-level warning, accounting for eight warning events.
- **Historical September 22–23 warnings:** source relocations/resets recovered;
  the notification TLS deadline and Plex transient were covered by the previous
  release review. The watchdog notices and rejected second instances align with
  the documented v3.10.131 deployment/recovery exercise. No new GL Drive Windows
  Application crash event was found in the preceding day.

## Changes

- After source discovery, classify the sole-receiver case as the existing
  already-present completion when every remaining participant is download-only.
  Require positive discovery of a receiving site; do not infer presence from an
  announce alone. No transfer or failure event is emitted for this no-op.
- Keep missing receiving sites, mapping/blacklist failures, never-source
  destinations, and topologies with no receiving sites on their existing paths.
- Six regression cases and a native FTPS lifecycle reproduction added. The
  reproduction failed against the previous code, then passed after the fix.
- Version 3.10.132; no configuration or persisted-data migration. README and
  changelog updated, including the previously omitted v3.10.131 entry.

## Remaining risks and rollback

- SYN and T: remain unavailable external dependencies; production is degraded.
- Existing race semantics treat a discovered release directory as already
  present. This change does not add a file-completeness audit or change filling
  behavior for those directories.
- Native smoke uses isolated loopback FTPS, not a remote glftpd BNC CPSV soak.
  Render checks do not cover every interactive flow or long-term stability.
- A launcher job that forbids breakaway can still terminate both app and
  watchdog; use the normal desktop/logon launch or verified job breakaway.
- Rollback uses the v3.10.131 installer; no data migration is required.
