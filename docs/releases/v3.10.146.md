## Defect found and fixed

Information-level lines get no automated triage, so this one surfaced only from a
manual read of them:

```
19:29:48.475 [INF] Relay: 81821696 bytes delivered but completion reply failed (The operation has timed out.) — counting as delivered; next scan verifies the dest copy
19:29:48.475 [INF] FXP complete: senna.s01e04.hdr.2160p.web.h265-croissants.r15 (superbnc.xxxxx.tw -> zephyr)
...
19:31:40.100 [INF] FXP complete: senna.s01e04.hdr.2160p.web.h265-croissants.r15 (superbnc.xxxxx.tw -> zephyr)
```

Transfer telemetry for the same file shows `bytes: 81821696` and then `bytes: 400000000`.
The volume is 400,000,000 bytes, so the first "complete" moved only 20% of it.

**Root cause.** `FxpTransfer.ExecuteRelay` treated EOF on the source data channel as
proof that the whole file had been delivered. When the 226 completion reply then failed,
it forgave the failure whenever `totalRelayed > 0`. It never compared the relayed bytes
with the listed source size. `ExecuteAsync` already receives that size (`fileSizeBytes`)
but did not pass it to the Relay path. So when the source aborted mid-file (EOF, followed
by an unanswered or failed reply), the partial file was reported as a success:

- ownership and `_destDelivered` counted it as delivered;
- the speed tracker was credited with 400 MB in 36 s;
- a telemetry row was written with no abort reason.

Only the next directory scan noticed the short copy on the destination. If the truncated
file had been the race's last outstanding file, the race could have closed before that
rescan.

**Fix.**
- `ExecuteRelay` now receives the expected size.
- The completion-reply forgiveness is gated on `RelayDeliveredInFull(relayed, expected)`:
  at least one byte relayed, and either the size is unknown (0, which keeps the old rule)
  or the relayed count reaches the listed size.
- A short relay now throws an `IOException` that names both byte counts. The normal
  failed-transfer path handles it: a warning, both connections poisoned (their completion
  replies may still be unread), backoff, and a retry.
- A file that grew on a still-racing source (relayed > listed) still counts as delivered.

## Remaining risks

- **External (unchanged):** SYN's FTP host is unreachable, and T: is not mounted, so
  downloads to T: stay parked.
- **Queue latency:** with `maxConcurrentRaces` 1 (the login cap), auto-races waited
  3.5–10 h in the queue on 2026-10-05, and the source relocations seen in this review
  come from that latency. This is a capacity limit, not a code defect.
- **Relay with an unknown size:** when the size is 0 (not listed), the old byte-count-only
  rule still applies, and the next scan remains the backstop.
- **Short relay with a successful 226 reply:** a source that reports success after sending
  fewer bytes than its listing goes through the normal (validated) reply path. This
  change does not add a size check there. No such event appears in the retained logs.
- `AgentRunner` logs "next run" three times when Windows fires `TimeChanged` (daily at about
  03:42). Only one run executes, so it is benign; noted for future reference.
