# GlDrive v3.10.117

## Log review and root causes

Reviewed all retained application logs, September 12–14, 2026, through approximately 09:01 PT on September 14. The installed version was v3.10.116 throughout. Historical crash dumps predate this window (latest July 20); Windows Application events 1000/1001/1026 contained no GlDrive crash in the last three days.

| Day | Lines | Error | Fatal | Warning |
| --- | ---: | ---: | ---: | ---: |
| September 12 | 22,470 | 0 | 0 | 38 |
| September 13 | 30,713 | 0 | 0 | 43 |
| September 14, partial | 19,586 | 0 | 0 | 17 |

All 98 warnings were classified: 53 SYN remount failures; 17 transfer failure headers plus 17 corresponding cause lines (10 STOR 425, four RETR 425, three RETR 550); two source relocation notices; nine notification poll failures (eight LIST 425 rejections and one control-reply timeout). The three RETR 550 failures belonged to two releases that the source relocated; the existing relocation handling followed them. Failed direct-route probes are quarantined and fall back to Relay as designed. No unattributed poisoned discards were found.

The September 12 11:23:26 notification timeout left an outstanding data reply. The pool safely quarantined it, but could only name the generic pending-reply condition. Tracing this call identified three related client defects:

- `NewReleaseMonitor` called the raw listing APIs, bypassing `FtpOperations.ListDirectory` and its explicit connection quarantine and cause attribution. Both root/category listings now use that shared implementation. Clean final LIST rejections still preserve reusable connections.
- The outer loop treated every `OperationCanceledException` as shutdown. An internal data TCP/TLS deadline could therefore permanently stop polling. Only cancellation of the monitor's own token now exits. This permanent-stop risk was reproduced in a regression test; the retained timeout was a `TimeoutException`, so the logs do not prove a permanent stop occurred in production.
- Category failures were logged only at Debug and then treated as a successful poll. Successful categories now continue updating, failed snapshots are retained, and a single contextual exception per incomplete cycle reaches the existing warning/backoff policy. Shutdown propagates immediately. First-time recovery seeds a category without announcing its historical contents.

## Remaining risks and rollback

- SYN's FTP endpoint remains unreachable. It is disconnected in the authenticated production status API; the retry ladder continues at five-minute intervals. Its network/server owner must restore reachability. No server configuration was disabled to conceal the failure.
- Intermittent remote 425 data-connection refusals persist. The client retries and backs off, but client logs cannot establish the server-side cause. Existing race connection hygiene and source relocation behavior remain covered by regression tests.
- A repeatedly failing notification category now activates the existing longer poll interval for the whole monitor. This can delay healthy-category notifications, while preserving their processing and avoiding a hot retry loop. Persistent failures use the existing first-three-warning/then-Debug policy.
- Before deployment the v3.10.116 heartbeat showed approximately 396 MB working set at 59.5 hours uptime. This is a bounded observation, not proof of leak-free long-term operation.
- Native smoke tests do not reproduce a remote glftpd BNC's CPSV stack. Internal cancellation/recovery is fault-injected in regression tests. Production observation cannot prove all possible failures resolved.
- Roll back using the v3.10.116 installer if notification recovery regresses. This release changes no persisted schema or credentials.
