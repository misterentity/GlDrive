# Bulk actions and Undo

Use Ctrl/Shift selection or Ctrl+A in Wishlist, Notifications, Downloads and the queued-race list.

- **Wishlist:** set resolution, pause/resume, mark Watching/Completed, or remove selected items. Updates preserve owned copies, pending downloads, source-floor permissions and other fields. Legacy quality profiles follow a changed resolution; custom profiles remain in effect and the result reports that fact. Removing a Plex Watchlist import retains its inactive identity so a later sync cannot re-add it.
- **Notifications:** download or race up to 25 selected rows through the normal admission paths. Selecting more than one requires confirmation showing the count, including when pressing Enter. Selections over 25 are rejected in full. Admissions run in the background and save once per affected store; races enter the ordinary queue. Remove selected rows or clear the currently retained history. New arrivals are never included in a pending clear. Feed mutes, saved views, wishlist matching and alert routing remain independent.
- **Downloads:** **Cancel selected** cancels selected queued or active work in a batch, keeping history and local files. Delete or **Remove selected terminal history** removes only completed, failed or cancelled history whose worker has finished. The Clear menu uses the same protection. Rows that are queued, running or still have active writers when the grace period ends are skipped. A retry that has already finished can be removed as terminal history. Local files remain on disk.
- **Race queue:** add the chosen site to visibly selected queued requests, remove its membership, or remove selected requests. Refreshes update rows in place and keep selection tied to the request identity. Membership changes use the existing queued-only B5 checks and one store save for the batch. Every operation rechecks the selected request identity, so an already started or replacement request is never changed. Bulk removal skips owned partials, cleanup requests and busy controls, and reports the skipped count. Existing explicit cleanup confirmations remain required for remote deletion.

Destructive bulk list edits display a **10-second Undo snackbar**. The rows stay present during that window; Undo cancels the pending removal. Only one removal may be pending, and another action cannot silently replace it. Closing the dashboard cancels pending work. Once applied, current identities are removed without restoring stale copies over concurrent updates. Finished race-card clearing also uses this grace period; persistent race history is retained.

These are explicit user actions. The fixed Undo window and terminal/queued checks change no automatic acquisition, login budget or network rate. Saved files and remote content are never deleted by these bulk controls.

The safe core keeps race scheduling order unchanged, as recommended by the verified roadmap lead. Persisted download reordering, inline title/year editors and certificate-pin clear/restore changes are outside this batch. Certificate controls retain their existing behavior; no bulk certificate action was added.

Automation can select the same visible rows with `ui.select_many` and execute the approved UI commands, including Undo. `ui.invoke` advertises a destructive hint because its command set includes persistent removals and membership edits. Destructive bulk automation uses the same pending snackbar rather than a separate immediate-delete endpoint.
