# Certificate-change decisions

GlDrive keeps its existing SHA-256 pins in `trusted_certs.json`, keyed by endpoint (`host:port`). First contact with an unseen endpoint still uses trust on first use. Matching pins continue to validate normally.

A changed pin now rejects the handshake immediately and opens a nonmodal **Certificate decisions** card. The affected endpoint is parked before any further FTP, ghost-recovery or TLS IRC connection attempt; other endpoints can continue validating. Closing the card or choosing **Keep rejecting** leaves the endpoint parked. Existing connections are not torn down.

Verify the full new fingerprint independently, then click **I verified this fingerprint — accept** to replace that exact pending pin. A stale card cannot accept a newer candidate. Reopen the cards from **Settings → General → Review Certificate Changes**. Normal connection recovery can resume after acceptance. If the server operator restored the original certificate, choose **Keep saved pin and retry** to release the hold without replacing the saved pin. A changed certificate will be rejected and parked again. This retry is available only by explicit local click. The outstanding-decision marker and old pin are persisted; after a restart the next handshake presents a candidate for local review, even if it offers the old pin. Disabling a server and restarting cannot turn an unresolved decision into first-use trust.

This is a mandatory correction to validation scheduling and the existing explicit trust boundary. There is no setting that enables automatic acceptance. Configuration writes, the agent, hooks, timed settings and snapshot restores cannot resolve a certificate decision. `certificates_list` exposes pins and pending decisions read-only; `certificates_trust`, `certificates_remove` and `certificates_clear` are no longer automation tools, because deleting a pin could otherwise turn a change into first-use trust. Local clear/remove actions preserve any pin with a pending change.

Pin writes retain their in-memory state and warn once if local persistence fails. An unreadable pin file is retried, then copied to `.corrupt` where possible. Recovered endpoint keys and the atomically saved `.endpoints` inventory preserve the distinction between prior pins and first use. Previously pinned endpoints require local review even if the next certificate matches; the decision explains the unreadable store, and saved-pin retry is unavailable. Known unpinned endpoints retain TOFU. If an old file is completely unreadable and has no recoverable inventory, prior pins cannot be identified, so endpoints require explicit local review until trusted individually. This recovery requirement survives restart. If quarantine fails, GlDrive does not overwrite the original pin file. SSH key management and a durable trust-history ledger are outside this change.

Legacy endpoint keys that differ only by letter case are combined without resetting the store. If their saved fingerprints conflict, the first saved pin remains authoritative; a different certificate requires local review. Loading these aliases does not rewrite the file or remove unrelated pins.

Pending decisions are associated with the stable server identity as well as host:port. Configuration patches, snapshot restores and ordinary settings saves reject endpoint re-keying, server ID replacement and server removal while that identity has an unresolved decision. Other setting changes remain available. A factory or editor test using an alias inherits the hold and saved pin; proxy changes do not clear it. TLS cannot be disabled on a pending IRC identity. The scheduler treats parked pools as unavailable and preflights both endpoints before borrowing either peer.
